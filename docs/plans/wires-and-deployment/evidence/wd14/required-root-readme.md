# Generated local v2 foundation

Experimental provider/project foundation. Inspect .jeeves/report.json for missing features and hooks. No application readiness or strict certification is claimed.

Node 24.21.0 and pnpm 12.16.1. Run `pnpm install --frozen-lockfile` then `pnpm build`. `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml` are yours: add a package with `pnpm add <name>@<exact version>`. `pnpm-workspace.yaml`'s `allowBuilds` says which packages' install scripts run: the template's dependencies run none (`protobufjs: false`), so neither command needs `--ignore-scripts`. Set a unique `COMPOSE_PROJECT_NAME` and three distinct free loopback ports: `LOCAL_HTTP_PORT`, `LOCAL_IDENTITY_PORT`, `LOCAL_OBJECT_PORT`. Run `pnpm first-run` once, `pnpm stop` to stop all profiles and `pnpm start` for normal restart. Reuse those exact values and private .runtime with the original Docker volumes. No resets or credential rotation occur. An interrupted single-use storage bootstrap requires manual inspection.

**Your own configuration.** `compose.override.yaml` beside `compose.yaml` is yours: export never writes it and `update:v2` never touches it. Docker Compose merges it into every command `pnpm first-run`, `start` and `stop` run, so give your modules their own `environment` and `secrets` there, or add a service of your own (for example a scheduler that calls your routes). A service of your own starts with `pnpm start` only when a generated service `depends_on` it, which your override may add; otherwise start it with your own `docker compose up`. Don't redefine a generated service's image, command, ports or healthcheck. A change applies at the next `pnpm start`.

Runtime PostgreSQL supports transaction-mode connection poolers: each standalone statement and explicit transaction uses a transaction-local server timeout; no session lock or connection-level statement timeout is required. `JEEVES_DB_POOL_MAX` is read once before clients open, accepts an exact decimal integer 1–100, and otherwise retains each pool’s configured maximum when absent. Invalid values fail without echoing their contents. Set it in application-owned deployment environment, not the diagram.

Migration owners/admin are mounted only into setup. `scripts/migrate.mjs` reaches PostgreSQL at `PGHOST` and `PGPORT` with `JEEVES_MIGRATE_TLS` (`disable`, or `verify-full` with an optional `JEEVES_MIGRATE_CA_FILE` and `JEEVES_MIGRATE_TLS_SERVERNAME`), read as a database's `_TLS` is; `PGSSLMODE` can't change it, and with `JEEVES_REQUIRE_TLS=true` it must be `verify-full` unless `PGHOST` is a socket directory. A credential is read from `JEEVES_SECRET_<NAME>_FILE` when that is set (an absolute path; `<NAME>` is the secret's name upper-cased, with `-` and `.` as `_`), else from `SECRET_DIR/<name>` (`/run/secrets/<name>`, where Compose mounts it). Runtime logins receive no implicit table access; features contribute explicit relation/view grants. PostgreSQL names are quoted and provider/composed-name limits refuse rather than truncate. Storage originals remain private; local public websites are a declared local-security limitation.

Cleanup only an owned disposable export: `docker compose --profile '*' down --volumes --remove-orphans` with its recorded project/ports, then remove its .runtime. Never run cleanup against a retained runtime.

Runnable processes: each application tile runs as `app-<id>` from `src/processes/<id>.ts`, healthy once its ready marker exists; HTTP processes answer readiness at `GET /readyz` (and `/healthz` for compatibility), and liveness at `GET /livez` on port 3000 inside the Compose network. `app-edge` publishes each public HTTP process at `http://127.0.0.1:$LOCAL_HTTP_PORT/api/<id>/` and answers `GET /healthz` itself; internal ones are reached only inside the network at `http://app-<id>:3000`. Required public services use the private `x-edge-stamp` gate. Local setup generates `.runtime/secrets/edge-stamp.env` (0600); nginx forwards those targets through `app-edge-stamp`, which overwrites client stamps. Keep its `JEEVES_EDGE_STAMP_KEY` private; optional `JEEVES_EDGE_STAMP_KEY_PREVIOUS` supports key overlap. Health stays reachable. The stamp never replaces user or workload authentication. A module's routes are under `/modules/<module id>`: a stub or a generated hook in `src/modules/` answers 501 `NOT_IMPLEMENTED` until you write it. A consumer module or worker template runs a loop on its queue (a topic's `<topic>--<id>` subscriber): "Not implemented" sends the message to `<queue>.failed` with one log line, other errors retry within the loop's limit (a stub's 5 times, waiting 250 ms doubling up to 10 s), an unreachable store waits 5 s and keeps the attempt, a failed `fetch` to an outside host keeps the normal retries, and `pnpm stop` drains the loops. Every store or channel a stub links to is provisioned for its tile with its links' widest access (a database login with CONNECT and USAGE on public, SELECT only on named published views and declared template views; a queue, topic or subscriber; a cache; a bucket key; a search service with no index), and `src/runtime/module-clients.ts` gives each stub real clients, each probed once at startup. A database a stub writes also has Jeeves's own `jeeves.idempotency_records` (`infra/postgres/<database>/050-jeeves-idempotency.sql`), which only the logins of the tiles whose stubs write it use: private legacy clients retain their 24-hour records. New public local operations use `defineLocalOperation` and the append-only 051 metadata migration: one authenticated account scope, committed replay before new-work admission, registered same-DB commands and atomic replay storage. Configure a private replay ring for secret responses; see .jeeves/extensions.md. Cleanup starts with the configured operation runtime and sweeps at most 1,000 expired committed rows every 60 seconds independently of traffic. Each stub declares the settings it reads in its file's `settings` export (`declareSettings` with `text()`, `integer()`, `url()`, `signingKeys(purpose)`, `sealingKeys(purpose)` and `optional(kind)` from `src/extension-api/index.ts`); its process reads them in its configuration pass, before any client is built or probed, and gives the same frozen values to the stub as `dependencies.settings` (rings yield purpose-bound handles, never raw keys): a missing or invalid one fails startup with `Invalid setting <NAME>`, never its value. `compose.yaml` sets none of them: set a setting in `compose.override.yaml`'s `environment`, and a signing or sealing ring as a file read as a credential is (above), `<name>` being the setting's name lower-cased with `_` as `-` (`PROBE_TOKEN` is `probe-token`), through its `secrets`; `processes.tiles[].stubSettings` in .jeeves/report.json names the files each process reads them from. Product SQL is application-owned: `infra/postgres/<database>/products.json` declares ordered migrations per namespace, tables, published views and registered parameterized queries/commands. Migrations run once under checksums and a transaction lock, as a namespace-only role; failed migrations roll back. Add versions, never edit applied SQL. Legacy `modules/*.sql` files are preserved but never executed. See .jeeves/extensions.md for the explicit baseline path. Product operations receive registered handles using separate product-only credentials; template tables remain protected. Only exact compiled table operations and named view audiences can be granted. `first-run` and `start` start them only while `processes.runnable` in .jeeves/report.json is true; its `processes.tiles` lists each process's routes, loops and provisioned stores. No restart policy: a failed process stays exited until `pnpm start`.

**Endpoints from the environment.** Each process with stubs checks the endpoints its clients and sign-in use in one pass before any client is built or probed, and reads each again as it builds that client, with no default: `JEEVES_DATABASE_<ID>_HOST` (a host, or an absolute Unix socket directory) and `_PORT` for each database, `JEEVES_CACHE_<ID>_HOST` and `_PORT` for each cache, `JEEVES_BROKER_HOST` and `JEEVES_BROKER_PORT` for the broker, and `JEEVES_TILE_<ID>_URL` (absolute `http:` or `https:`, with no credentials, query, fragment or whitespace) for each tile its stubs call, where `<ID>` is the tile ID upper-cased with `-` as `_`. A missing or invalid one fails startup with `Invalid endpoint <variable>`, never its value (several at once: `Invalid configuration: <message>; <message>`). Each database and cache also reads its transport, `JEEVES_DATABASE_<ID>_TLS` or `JEEVES_CACHE_<ID>_TLS`, with no default: `disable` (plain text, which `PGSSLMODE` can't change) or `verify-full` (TLS that checks the certificate chain and the host name); with `verify-full`, `_CA_FILE` is an optional PEM file (else Node's roots; one that can't be read fails startup with `Unreadable CA file <variable>`) and `_TLS_SERVERNAME` the optional name the certificate carries when it isn't the host (a managed instance reached by a private address). With `JEEVES_REQUIRE_TLS=true` (else unset), startup fails with `Insecure endpoint <variable>` for a database or cache whose transport isn't `verify-full` (a database's Unix socket directory is local transport and passes), a `JEEVES_TILE_<ID>_URL`, `OIDC_ISSUER` or `OIDC_JWKS_URL` that isn't `https:`, and any `PUBSUB_EMULATOR_HOST`; the broker, object storage and search are plain text and aren't checked. With the switch, `NODE_TLS_REJECT_UNAUTHORIZED` must be unset or `1`, else startup fails with `Insecure endpoint NODE_TLS_REJECT_UNAUTHORIZED`: `0` would turn off certificate checks for every client that leaves them to Node. `compose.yaml` sets the local values (`disable`, and no `JEEVES_REQUIRE_TLS`); a deployment sets its own. Object storage and search are still reached at their local names. **Local configuration summary.** This lists explicit Compose environment keys, required External API URLs and the optional workload secret-file override; it excludes env_file and other secret-path overrides and other optional reads. For installed runtime environment names per process, see the [deployment guide](deploy/README.md) and [machine-readable contract](deploy/contract.json). Those inventories cover installed runtime reads; review application-owned settings and SDK conventions separately. `processes.tiles[].environment` in .jeeves/report.json is also a local configuration summary, not the deployment inventory:

- `app-edge-stamp`: `LOCAL_HTTP_PORT`
- `app-front`: none
