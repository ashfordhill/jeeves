# WD11 — transaction-pooler database access

Runtime source is changed through the v2 templates and emission. `transaction.ts` applies the
pool's configured `SET LOCAL statement_timeout` immediately after BEGIN; standalone queries use
that same transaction boundary. `query_timeout` stays 500 ms beyond the configured statement
budget. A deadline holds the checked-out connection through actual commit/rollback settlement;
unknown COMMIT still discards the connection and never retries an effect. A context that expires
while acquiring a connection sends no SQL and releases the unused client normally.

`sweepExpired` acquires `pg_try_advisory_xact_lock` inside its deletion transaction, skips a lock
held by another copy, and releases through commit/rollback. The SQL and 1,000-row/status/expiry
bounds remain unchanged. Product mutation now restores `SET LOCAL ROLE NONE`. The audit found no
other runtime session locks, LISTEN, named prepared queries, temporary tables or session SET:
local operations, favorites and durable cleanup already use transaction advisory locks; browser
refresh keeps its existing bounded transaction-local lock/statement/idle overrides. Setup and
product migration tools remain separate administration, including their existing session setup.
Application-owned SQL must also obey transaction pooling; private legacy raw SQL is not a hostile
code boundary. New public registered SQL remains checked by API8.

`JEEVES_DB_POOL_MAX` is read once during Postgres module initialization, before clients can open.
Exact decimal integers 1–100 override every runtime pool in that process. Absence keeps each
pool's former configured maximum. Invalid input fails with a name/range-only message. No diagram
setting was added. Deployment inventory follows actual shared clients/constructor imports:
SQL-free exports and HTTP shells with no SQL imports omit the variable; a no-SQL process importing
shared SQL clients reads it. The independent WD09 expectation and actual-reader audit cover this.
The Postgres scaffold now contributes its transaction dependency even for a SQL-only template
with Runnable processes off, while installed durability retains single ownership of that helper.

Recovery readiness requires a successful committed database query/probe, not merely a connection
to the pooler. The one tracked probe slot stays occupied through actual driver settlement after
its two-second deadline. A result arriving after that deadline does not mark readiness; a new
successful probe can recover, and shutdown prevents new work and late readiness changes.

subsequent sweep recovery, timeout-setup failure before effects, strict pool parsing and one-time

all transaction advisory locks, newly including cleanup. It now denies precisely the original
operation lock using `hashtextextended`; the expected one-row cleanup assertion is unchanged.

then passed 26/26. Other first focused failures were exact BEGIN/SET LOCAL/sweeper trace changes,
a former connection-option expectation and the recovery probe fake. No assertion was relaxed.
The recovery regression retains its original 15-second stall and now also checks late-result
refusal, fresh-probe recovery, actual COMMIT and shutdown suppression.

Two public CLI scratch exports cover the 94-file WD09 composition and a 46-file processes-off
positive reader with no durability contributor. Actual generated API8 checker and TypeScript
7.0.2 pass using existing dependencies; no install was needed for these scratch checks.
Initial minimal-export attempts were refused for incomplete old preset selections, an active
scheduled task with processes off, then a redundant off command; the final new minimal design
uses supported authoring operations. Generated implementations were never patched.

[Pin delta](wd11/pin-delta.json) was inspected before updating exact expectations: the two SQL-rich

## Native pooler evidence

The opt-in integration flag supports only `--suite=rg-mechanisms`; unsupported combinations fail
before run/resource creation. It uses
`edoburu/pgbouncer@sha256:68969403ee54dbf98601b49a1e92db644a9fdeed5c40969f7f0adce5193ac5b8`
(the linux/amd64 manifest for v1.25.2-p0), `pool_mode=transaction`, server pool maximum 2 and
`max_prepared_statements=0`. Application pools use the external maximum 3. No pooler port is
published; generated edge/identity ports are unique loopback bindings under the task's recorded
UUID Compose project. This is disposable harness configuration, never production provisioning.
PgBouncer's [mode/config semantics](https://www.pgbouncer.org/config) and the
[image entrypoint](https://github.com/edoburu/docker-pgbouncer/blob/master/entrypoint.sh) were
checked while choosing the pinned harness configuration.

Both existing RG23 scenarios run unchanged assertions, including browser refresh's 1,000 ms
request deadline. Generated API/browser/worker database paths go through the pooler. The catalog
COMMIT gate and lost-COMMIT-response TCP proxy also use the pooler upstream. Setup migrations and
explicit raw administrator/permission inspection still reach Postgres directly; those observations
are administration/permission evidence, not pooler-path runtime evidence.

The [first native attempt](wd11/native-first.log) is a failure, not a pass: it observed transaction
mode and nine clients but browser concurrent refresh returned 503/503 at the existing deadline;
the second fixture encountered a harness sibling-directory collision. Both stacks were cleaned.
Per-fixture pooler directories fix the collision. The first attempt overlapped broad regression
checks; a later serial result, not that coincidence, determines the final behavior claim.
All 35 emitted link-flow runtime payloads are [byte-identical](wd11/native-runtime-comparison.json)
between the first and second attempts; only inventory/tests/harness details changed.
