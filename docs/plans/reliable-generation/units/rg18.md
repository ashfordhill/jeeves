# RG18 — Receipt retention and consumer progress

Read shared documents and evidence E8/E10. Prerequisite: RG17.

## Goal

Complete the existing deduplicating consumer mechanism with bounded maintenance and truthful
progress/failure state.

## Work

- Extend existing receipt/event-counter/consumer adapters; preserve atomic receipt plus product
  effect before ACK. Hooks parse/map data or invoke scoped product commands; no raw ACK control.
- Add a declared replay/delivery horizon and compatible receipt retention. Refuse an insufficient
  retention promise. Identity is stable across timestamps/date partitions; a modified event date
  cannot bypass deduplication or payload-conflict detection.
- Use scheduled, bounded cleanup independent of arrivals. Index the cleanup path and expose
  cleanup backlog/last success; do not promise an arbitrary ingestion capacity from a fixed batch
  size. Never delete active work or records still inside the supported replay horizon.
- Record worker heartbeat, last durable progress and available backlog state separately. Unknown
  backlog stays unknown; a stopped worker cannot appear healthy just because its last event was
  quick. Define quarantine and explicit safe requeue through an internal operation/CLI, without
  a new public administration service.
- Apply common behavior to the existing Event counter and the generic delivery adapter, keeping
  product aggregation policy separate. Preserve provider-specific delivery semantics and refuse
  combinations whose semantics are unsupported.

## Acceptance

Duplicate deliveries do not repeat effects; a crash after commit but before ACK remains safe.
Changed timestamps cannot defeat identity. Cleanup runs with no traffic, respects the horizon,
and reports backlog rather than claiming unbounded capacity. A stopped worker becomes stale;
an idle live worker remains distinguishable. Poison input and unavailable storage take different
recovery paths. Quarantine replay preserves original identity.

## Emitted surface and checks

Receipt/consumer/counter runtime, retention/progress schema and maintenance bindings. Standard
checks plus boundary-time, duplicate/conflict and stale-heartbeat tests. RG23 checks broker
redelivery and worker loss. No QRWTY-specific analytics tables, retention gate or erasure saga.
