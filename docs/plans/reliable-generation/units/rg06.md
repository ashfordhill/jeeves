# RG06 — Logical ownership and precise runtime grants

Read shared documents and evidence E4. Prerequisite: RG05. Owner decision D5 applies.

## Goal

An API and its separate worker can share declared owned data without weakening boundaries between
unrelated services or exposing every published view to every reader.

## Work

- Reconcile existing logical owner/role declarations with store access used by stub resolution,
  client wiring and generated grants. Do not add a second ownership system. Support distinct API
  and worker roles within an explicitly chosen owner, with separate credentials.
- Provide the smallest normal authoring operation needed to declare that ownership relationship
  when connecting a worker to existing owned state. It must be an explicit choice, not automatic
  merger of unrelated owners. Use existing process tiles; add no owner cards/deployment controls.
- Compile precise product-table operations and published-view reader audiences. Replace blanket
  SELECT-on-all-published-views grants. Keep template-internal tables out of product access.
- Give same-owner modules a declared shared product-state namespace with an unambiguous owner;
  do not require them to rely on a schema owned by whichever module happened to initialize first.
- Update normal mouse/chat commands, validation, blueprint and generated permission descriptions
  together. RG07 supplies migration/version execution for the declarations.

## Acceptance

An API and worker with the same owner can perform their declared operations using different
logins; a third service cannot write those tables. A reader can read its named view but neither
another published view nor underlying private tables. A conflicting owner refuses the connection
without partial changes. A label rename changes no permission identity. No application credential
has migration/DDL privileges. All checks apply to generated SQL, not merely TypeScript interfaces.

## Emitted surface and checks

Normalized ownership/access, login/grant metadata and SQL, scoped client types and shared-state
declarations. Standard checks, PGlite permission cases where supported and mouse/chat parity;
real database roles are exercised at RG14.

## Not included

No tenant system, enterprise IAM UI, cloud roles or implicit cross-owner writes.
