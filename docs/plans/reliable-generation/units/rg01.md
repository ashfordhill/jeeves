# RG01 — Versioned capability model and migration boundary

Read the packet's shared documents and evidence E1. **One fresh agent; this unit only.**

## Goal

Extend the existing normalized generation model with the finite capability/extension contracts
the approved packet requires. Introduce the version boundary before changing handwritten APIs.

## Work

- Update `jeeves/packages/spec/src/{generation-resolver,generation-catalog,generation-support}.ts`
  and generator `src/v2/{registry,assemble}.ts`, `src/update.ts` and `src/v2/update-cli.ts`.
- Add serializable records for callable capabilities, effect class, logical owner/role, declared
  access, required caller identity, lifecycle owner and extension API version. Use stable IDs and
  source paths. Keep saved design schema compatibility; do not build another intermediate model.
- Register only facts consumed by an implemented emitter/check. Future capabilities in this
  packet remain uninstalled, not optimistic supported flags. Implement a small existing-module
  fixture to demonstrate each new record's consumer.
- Record the generated extension API version in manifest/report metadata. An update encountering
  an incompatible handwritten extension reports its paths and refuses to apply automatically.
  A check/dry run makes no changes. Provide an explicit migration acknowledgement mechanism with
  no automatic rewrite of handwritten code; its completion checks the new interface/build.
  Use a staging export/copy to validate migration against new generated files before applying,
  so the old checkout need not already contain the incompatible new runtime to pass the check.
- Add a concise generated extension guide naming the contract version and future public API
  location. The guide is technical documentation, not another canvas configuration panel.

## Acceptance

Equivalent diagrams normalize deterministically; JSON serialization round-trips without executable
or TypeScript-specific values. Missing required capabilities have an actionable source location.
Old diagrams remain readable. An old modified hook survives an incompatible update byte-for-byte,
and a newly generated app records its API version. Existing compatible updates still work.

## Emitted surface and checks

Normalized model, manifest/report, generated extension guide and relevant update diagnostics.
Run standard code-unit checks, resolver/schema tests and an offline update fixture. Inspect changes
to existing pins; frozen v1 remains unchanged. No Docker checkpoint in this unit.

## Not included

No new runtime capability, general schema language, Go/Rust emitter or root-file change.
