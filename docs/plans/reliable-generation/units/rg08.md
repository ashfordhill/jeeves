# RG08 — Keys, signatures and sealed values

Read shared documents and evidence E5/E6. Prerequisite: RG07; uses RG02 lifecycle.

## Goal

Give generated mechanisms one tested implementation of key rotation, signatures and sealed
values without exposing key material to product policy.

## Work

- Build on existing `settings.ts.template` key-ring validation and current crypto primitives.
  Add a small generated keys module with purpose-separated signing/verification and authenticated
  encryption. Use platform cryptographic primitives; do not invent cryptography.
- Read rings once through the configuration/lifecycle pass. Expose only declared purpose-bound
  handles where application code needs a signed cursor or similar value; raw keys stay internal.
- Version envelopes, bind authenticated context to the correct scope, identify the signing key
  and verify against allowed retained keys. Validate input size and encoding. Corrupt or unknown-key
  values fail safely without logging their contents.
- Establish the mechanisms needed by replay, workload credentials, HMAC ingress and sessions;
  do not implement those features here. Generated package assets may use existing dependencies;
  no root dependency change.

## Acceptance

Current-key writes and old-key reads work during rotation; removed/unknown keys fail. A value
cannot be replayed under another purpose or account/context. Tampering, truncated envelopes,
invalid encodings and oversized inputs fail. Startup errors name the configuration, never key
bytes. Policy hooks have no raw-key or secret-file handle.

## Emitted surface and checks

Keys runtime/public opaque handle types and configuration wiring. Standard checks plus fixed
crypto vectors, rotation and negative cases. No Docker or live identity provider.

## Not included

No key management service, cloud secret provisioning, key-management UI or provider pack.
