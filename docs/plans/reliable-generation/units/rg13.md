# RG13 — Callable cache reads with explicit freshness

Read shared documents and evidence E3/E7. Prerequisite: RG12.

## Goal

Let custom features use the existing cache mechanism directly and safely distinguish immutable
records from mutable/versioned records.

## Work

- Refactor the existing positive cache reader through the shared callable binding. Preserve its
  useful eligibility/codec/load hooks, but expose only scoped loading and pure policy interfaces.
- Keep immutable-positive behavior as its own contract. Add the finite versioned-read behavior
  justified by QRWTY, using RG11 compare-version writes and absolute validity. Do not silently
  claim the old immutable template handles mutable state.
- Return the freshness/validity metadata callers need for a final check after another operation.
  Bound in-flight fills and waiting callers under RG03; coalesce compatible same-key work within
  one process without making correctness depend on that map.
- Optional cache failure falls back to the authoritative read under a bounded documented policy,
  then recovers. A stale or expired value is never refreshed merely by serving it. Cache policy
  does not grant access to private records or bypass the product eligibility check.
- HTTP exposure remains an explicit adapter; in-process use does not create an accidental second
  public endpoint. Keep the normal UI surface small and fully generated.

## Acceptance

Existing YouTube-style immutable eligibility works. A mutable redirect-like record cannot regress
after a slower old fill, and validity cannot lengthen through transport delay. Expiry during a
later operation is observable to its caller. A cache outage recovers without a process restart;
overload remains bounded. Unsupported freshness combinations refuse before generation.

## Emitted surface and checks

Cache runtime/adapters, hook contract and callable/HTTP wiring. Standard checks plus immutable
and mutable fixtures. RG14 covers real shared cache behavior; no benchmark or general cache DSL.
