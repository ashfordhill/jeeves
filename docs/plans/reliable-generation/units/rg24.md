# RG24 — Regeneration, explicit migration and maintenance evidence

Read shared documents and evidence E10. Prerequisite: RG23.

## Goal

Prove that the improved generation can be adopted without silently destroying handwritten work
or product data, and measure whether application authors actually do less infrastructure work.

## Work

- Use scratch copies of an existing fixture/export and the new fixtures. Exercise RG01's
  incompatible-hook refusal, explicit handwritten migration and subsequent compatible update.
  Preserve original QRWTY/YouTube repositories and historical exports.
- Seed durable product data and pending work before update. Change a supported diagram setting,
  regenerate through the public update command and verify behavior changes while hooks/data remain.
  Check label-only rename separately from explicit identity migration.
- Run two consecutive identical regenerations to show determinism/idempotence. Verify no temporary
  compatibility runtime has become an indefinite second implementation. Old diagrams remain
  readable; a remaining migration gap is explicit and cannot be reported as completed support.
- Measure each fixture's generated/handwritten backend source using the existing method, alongside
  handwritten SQL and maintenance actions. Record reviewed backend scope; exclude UI. Count how
  many places a product change touches and whether it requires editing a generated file or writing
  coordination/recovery code. Do not optimize bulk to reach 60%.
- Compare the demonstrated mechanisms with the named QRWTY A gaps/B lessons, not with a claim of
  a new full A/B product benchmark. Document precisely which lessons were proved and which remain
  outside scope. No new baseline app implementation.

## Acceptance and output

`evidence/rg24/migration.md` contains the actual migration steps and preservation results;
`evidence/rg24/maintenance.md` contains reproducible counts and change examples. A compatible
update preserves modified hook bodies byte-for-byte. An incompatible update refuses before
mutating them. Existing product data and accepted pending work survive the supported update path.

Use the existing regeneration harness and a bounded selected scenario; standard checks for code
changes. Do not deploy, touch original field apps or conceal manual migration cost in the metric.
