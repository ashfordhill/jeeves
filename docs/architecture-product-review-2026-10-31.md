## UI/UX comparison and product observations

Excalidraw's quiet tool island, generous canvas and direct starting prompt reduce the decisions before the first useful action. Automation-pitch contributes a coherent paper/ink palette, stable control footprints, strong selection and contextual editing. Its visual history shows why tiny fitted islands, captions repeating the obvious, shifting controls, clipped fields and implicit application of drafts harm usability. Jeeves should keep labels where execution semantics matter, and make the common path visually compact.

Jeeves's current C4 component view is readable at normal scale and separates provided delivery from project-owned domain work. The new event form is usable and accessible, but a long all-events form is less efficient than a compact list with one focused editor. The resource editor should begin with that focused layout, retain a visible Save/Cancel footer, show concrete effects and preserve the selected neighbor after draft removal. It should use the existing visual language rather than add another theme engine.

qrwty's Library, Studio and Analytics now form a coherent dark product shell aligned with the existing qrwty direction. The Studio has visual presets, a large live QR preview, finite customization, saved revisions and immutable exports. Analytics states that scans are requests and provides bounded ranges, chart/table and exports. The [Studio](evidence/p17/studio-desktop.png), [analytics](evidence/p18/analytics-desktop.png) and [fresh recipe](evidence/p19/product-desktop.png) evidence reflects the current unchanged implementation. Future product work should be driven by a concrete user journey (for example selection/search at larger libraries or a richer customization preset), with stable QR identity and saved revision ownership. This review does not regenerate or modify live qrwty.

## Architecture references and extraction decisions

The [five pinned source reviews](reference/enterprise-architecture.md) remain useful for specific responsibilities: Payload for collection/transaction boundaries; Umami for authorization/query/presentation separation; Medusa for typed domain steps and delivery state; Zulip for synchronous/background boundaries; Backstage for identities, references and processing findings. Each has documented tradeoffs and license boundaries. No reference is treated as a perfect application, and no upstream source has been transplanted into a Jeeves runtime. The P21/P22 non-QR consumer is concrete follow-through on the Medusa/Zulip-inspired delivery boundary; the first proof is not a reason to pull in a complete commerce/collaboration stack.

Retain the repeatable source cache and named verification commands. Prefer a short script/profile for an expensive repeated operation; add MCP/Skills only when they solve an actual interface/reuse need. Avoid another automation layer for already available commands. The deferred exhaustive testing/capacity/security campaign remains a separate future prompt, as requested.

## Selected next work

**P23: structured resource authoring.** The existing deterministic backend should be directly accessible by mouse: owner/internal resources, typed fields, ownership relations, finite CRUD capabilities, selected store and a readable endpoint preview. Preserve exact domain extension contracts and immutable storage identities. Handle recipe-provided definitions conservatively. This delivers the largest immediate reduction in routine model dependence without adding a new runtime or widening infrastructure scope.

After P23, reassess the next gap: a finite generic resource workspace/recipe could remove repeated frontend CRUD work; application/architecture verification evidence could become easier to inspect; recipe evolution and operational policies need their own explicit contracts. Choose one bounded package at a time. Repeat the overall gap review after subsequent packages; this is an interim review through P22, not a declaration that every enterprise application can already be built.
