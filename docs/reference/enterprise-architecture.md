# Architecture references for deterministic Jeeves components

Inspected 2026-10-30. These are selected architectural references, not a ranking of perfect applications or a certification of their security. Each has useful separations of responsibility and visible tradeoffs. The [source catalog](architecture-sources.json) pins actual implementation and license files by commit and SHA-256. `pnpm references fetch all` retrieves only those files; `pnpm references verify all` checks the cache offline. No upstream code has been incorporated into a Jeeves runtime or generated application by this research.

Selection favors explicit contracts, clear ownership, useful extension seams, migrations, failure handling and an application that exercises the pattern. Popularity alone is insufficient. The snapshots are the inspected branch revisions, not dependency recommendations or promises that those development branches are stable releases.

The later [backend benchmark reference packs](backend-benchmarks.md) add released source snapshots
to the same cache catalog without replacing these five historical pins. P60a supplies Discourse and
P60b supplies Vendure; Zammad and the combined review remain P60c work. Their provenance is distinct
from these original branch snapshots and from any runtime adoption or observed benchmark coverage.

## Selected applications and inspected seams

| Reference | Useful pattern | Concrete limits and adoption decision |
| --- | --- | --- |
| **Medusa**, commerce | Workflow definitions compose typed steps with separate invocation and compensation. Event delivery tracks completed subscribers during retries. | Compensation is domain work, not a database rollback. Redis delivery defaults to one attempt unless configured. Study the shared MIT workflow/event infrastructure; exclude proprietary RBAC/SSO paths. Do not install a commerce stack to implement QR saving. |
| **Payload**, CMS/application backend | Collection configuration feeds operations; read access constraints are combined with query filters. A request carries transaction context through nested calls. | Hooks are arbitrary code and can obscure side effects. In this pinned revision Local API `find` defaults `overrideAccess` to false; explicit bypass still exists. Jeeves should expose narrow typed extension hooks and keep authorization inside generated boundaries. |
| **Umami**, analytics | Route authorization, validated query shape and SQL aggregation are separate. One aggregate interface supports relational and ClickHouse implementations. | Its richer visitor/session model is not qrwty's scan count. The inspected date validator requires a range but does not itself cap its span. Start with bounded owner-scoped Postgres aggregates; add another engine only when evidence warrants it. |
| **Zulip**, collaboration | Separate synchronous application work, real-time delivery and background workers. Queue publication can be deferred until database commit; workers have timeouts, statistics and error recording. | An after-commit callback alone does not close the crash window between commit and publication. Reproducing its complete Django/Tornado/RabbitMQ stack would be wasteful. Use a transactional outbox for a later Jeeves durable-delivery component and state its guarantees precisely. |
| **Backstage**, developer portal | Versioned entities, stable references, typed relationships and processing diagnostics describe a software ecosystem. APIs and infrastructure are separate concepts from software ownership. | A catalog is not a generator, and Backstage's “Component” is not necessarily a C4 component. Use its separation of identity, relations and presentation as a reference; keep Jeeves's model authoritative and bind views to real generation capabilities. |

## Candidate building blocks

All entries below are **proposed**, not implemented by P16. C4 associations describe responsibility and deployment, not new drawing primitives. A component must earn a version and a place in the executable catalog through a real consumer. Existing owner CRUD/sessions, validated commands and QR renderer are the starting implementations, with their actual evidence in the handoff.

| Candidate | Deterministic contract and responsibility | Model/human extension seam | First proving consumers |
| --- | --- | --- | --- |
| Policy-scoped resource + transaction context | API component: typed fields, ownership relation, finite capabilities, validated input and database transaction passed to nested operations; deny by default | Domain policy predicates through a typed principal/context; no accidental raw-query bypass | qrwty artwork revisions; document/inventory revisions |
| Immutable revision | API/storage component: parent authorization, pinned renderer/schema version, stable public identity, idempotent save, bounded history, immutable export input | Domain content validator/renderer through a versioned interface | qrwty Studio; document configuration editor |
| Bounded analytics query | API/query component: owner predicate, `[from,to)` UTC interval, allowed dimensions, maximum range/result size, declared count semantics | New reviewed aggregate definitions; no free-form SQL from a diagram or prompt | qrwty scans; inventory movement counts |
| Analytics dashboard | Web component: contract-bound metrics, range controls, chart/table, loading/empty/error states and accessible exports | Labels and reviewed visualization choices | qrwty owner dashboard; inventory history |
| Transactional event delivery | API + worker + database containers: outbox in the write transaction, schema-versioned events, deduplication key, finite retries/backoff, visible exhausted state | Idempotent business handler; explicit external side-effect semantics | QR-change webhook fixture; order notification fixture |
| Compensating workflow | Worker component: versioned step graph, typed inputs/outputs, persisted state, timeout and compensation policy | Named domain steps and their compensations; no generated guesses about reversal | Fulfillment/reservation fixture after simpler delivery works |
| Event subscription | API/realtime boundary: authorized topics, bounded buffers, cursor/resume semantics, reconnect and expiry behavior | Domain event projection | Long-running export progress; inventory changes |
| Architecture catalog + validated relations | Design-time model: system/context ownership, container bindings, component responsibilities, API/resource relationships and actionable findings | Unsupported behavior clearly identified as project-owned work | qrwty and a second non-QR application design |

Proposed order: finish Studio, owner analytics and deterministic product recipes; add the C4/configuration surface; then implement the smallest useful event-delivery/reliability slice with a non-QR consumer. Workflow/realtime expansions follow actual demand. Do not accumulate decorative catalog entries that cannot generate anything.

## Extraction and evidence rules

Before adopting a pattern, specify its input/output schema, authorization and tenancy boundary, version/migration behavior, ownership paths, failure behavior and deployment needs. Prefer a small generated facade around a maintained library or a narrow Jeeves implementation over transplanting an application's internals. Pin versions and keep upstream source/notice provenance for any future direct copying; this package licenses no proprietary code and adds no upstream runtime dependency.

Each capability should report **proposed**, **experimental**, or **verified for a stated envelope**, alongside its evidence and limitations. “Verified” must name the consumer, configuration, version and checks; it never means bug-free. Expose deterministic coverage by behavior, not a percentage inferred from lines of generated code. Model-owned extension work remains visible and cannot silently replace protected runtime behavior.

The user's current priority is implementation and product refinement with focused verification. Keep lint/types/offline gates, the changed behavior's checks and boundary checks for authorization, migration, export or browser changes. Defer exhaustive configuration matrices, load/soak/chaos campaigns, disaster recovery, penetration reviews and capacity certification. Record those gaps in the adopting component's documentation and handoff; do not attribute every generated-app defect to the implementing model or human.

## Implemented follow-through through P18

The P16 candidate table above is the original proposal. Studio now consumes the versioned QR renderer and shared configuration editor (P17). P18 introduces experimental `@jeeves/analytics@0.1.0` and product-ui 0.3.0 count/metric presentation. Its owned-parent/child-event contract validates physical descriptors, takes owner identity only from the authenticated service, bounds UTC ranges to 90 days and top results to ten, and executes parameterized Postgres aggregates inside a read-only repeatable-read transaction with a five-second per-statement timeout. qrwty is the actual HTTP/Postgres consumer; an inventory movement example verifies the same non-QR interface offline. No Umami source code or dependency was copied.

These deliver the proposed separation of authorization, query bounds and presentation for a stated envelope. They do not establish production capacity, visitor identity, analytics rollups or autonomous template wiring. Evidence and deferred checks are recorded in each package's README and implementation handoff. P19 now supplies the QR Studio implementation, immutable artifacts and complete protected acceptance through a versioned deterministic product recipe. Fresh generation and zero implementation-model planning are verified for its bounded configuration. P20 now supplies intentional context/container/component views, explicit architecture bindings and structured product configuration over the same semantic model.


## P21 durable-delivery follow-through

Experimental `@jeeves/durable-events@0.1.0` implements the proposed durable-delivery core: transactional tenant-scoped enqueue, canonical event identity, stored policy snapshots, competing Postgres claims, expiring fenced leases, finite retry/backoff, visible exhausted state and an atomic database-effect receipt. The [component contract](../../packages/durable-events/README.md) explains cooperative cancellation and the difference between external at-least-once attempts and committed database-effect deduplication. The [immutable compiled artifact](../../artifacts/durable-events/0.1.0/manifest.json) records exact source/archive hashes.

Medusa's explicit subscriber/retry separation and Zulip's transaction-aware publication informed the responsibility split; no upstream runtime code was copied. The queue stores its event inside the business transaction, rather than relying on an after-commit callback for publication. Four focused disposable PostgreSQL inventory scenarios cover atomicity, tenant identities, competing claims, stale ownership, retry/exhaustion, restart and lost acknowledgements. This proves the documented local envelope, not fleet capacity, exactly-once network delivery or general enterprise readiness. It has not been silently added to qrwty. P22 will integrate the working component into generation and visual configuration.


## P24 resource-workspace follow-through

Experimental `@jeeves/resource-workspace@0.1.0` separates a strict finite display contract, same-origin session/CSRF transport, accessible account screens and owner-resource lists/forms. Payload's reviewed collection/authorization separation informed the boundary; no upstream runtime code was copied. The API remains the authorization authority. The component supports the current generated field/relationship/update contract, finite visual presets and bounded cursor pages, without inventing totals or access rights. Its [contract](../../packages/resource-workspace/README.md) and [compiled artifact](../../artifacts/resource-workspace/0.1.0/manifest.json) record exact responsibilities and hashes.

A disposable Inventory consumer proves the compiled runtime with real generated session/resource APIs, Postgres, owner isolation, paging, related records and responsive accessibility. This is a focused envelope, not enterprise certification. The consumer integration is explicitly reviewed project source in P24; P25 will bind it to actual diagram capabilities and generated ownership. The released product-ui 0.3.0 archive is reused byte-for-byte. Live qrwty and the QR recipe are unchanged.


## P25 executable workspace follow-through

The [resource-workspace attachment](../../templates/resource-workspace/README.md) now binds the P24 runtime to an actual session-resource API and derives its fields, relationships and capabilities from that contract. Stable IDs carry display selection; labels/preset/page size remain finite user choices. Protected composition and immutable artifacts remove routine frontend implementation work, while additive content and domain API behavior stay explicit. The generated Inventory proof uses no hand-written application root and seeds no implementation tasks. C4 projects the real API dependency, supplied workspace responsibilities and additional notes separately. This is a usable bounded resource application, not an arbitrary enterprise workflow engine.


## P26 editable architecture follow-through

The [resource application starter](../../starters/README.md) packages P25's executable composition with deliberate C4 person/system intent and a useful initial layout. Its versioned/hash-checked snapshot is copied into a new editable design; `startedFrom` records origin without pretending to be a protected implementation or verification result. The first-project chooser and current-model configuration use those real bindings. This follows Backstage's reviewed identity/reference/provenance separation while keeping Jeeves's executable design authoritative; no Backstage code or dependency is copied. The disposable factory-to-app proof consumes fresh private environment values, needs zero implementation tasks and preserves existing credentials/custom content during regeneration.
