# Local HTTP pool audit · P31

Reviewed against P30 (`a3877cf`) before adding any pool to the generator. This is a bounded eligibility analysis, not enterprise certification.

| Responsibility | Existing implementation | Pool implication |
| --- | --- | --- |
| Account/session/CSRF | `templates/rest-api-server/runtime/src/sessions.ts`: shared `app_user`/`app_session`, token hashes, database expiry and CSRF token; HttpOnly cookie, exact public Origin | No sticky session is needed for these generated operations. Every instance must share the same database and public origin. |
| Request identity | `resources.ts`: WeakMap keyed by the actual Fastify request; configured public origin is process-local but constant | Per-request authentication state is safe to reconstruct on any instance. No instance-local login session cache. |
| Resource data and ownership | `resources.ts`: owner predicates and parent checks in SQL; database ordering/cursors | Ordinary generated owner CRUD is the first eligible behavior. An application-specific extension has separate semantics and cannot inherit this claim. |
| Migrations | Postgres runtime `migrate.ts` uses a session advisory lock around Drizzle; `resource-migrate.ts` uses a transaction advisory lock and immutable hash journal | Multiple instances can enter startup without independently applying the same migration. This does not authorize arbitrary schema changes or a new migration strategy. |
| Connections | Postgres runtime defaults to five connections per process | Two/three instances budget ten/fifteen application connections, plus other consumers, health/startup work and administration. More instances do not imply more database capacity. |
| Readiness/shutdown | HTTP runtime `/ready` checks actual dependencies and shutdown state; graceful close drains requests before dependency teardown, with a finite process deadline | Probe each instance, exclude failed readiness, keep proxy/process/Docker deadlines explicit. A successful health probe cannot promise the next request succeeds. |
| Admission and client IP | No auth rate limiter was found in the current HTTP/REST runtime; Fastify does not enable trusted proxy parsing | No global rate-limit claim. The backend sees the proxy connection IP. Forwarding headers are not authorization or audit identity. A future trusted-proxy/admission contract needs its own release. |
| Project features and workers | Features can add routes, startup/stop hooks, files, process memory and timers; durable delivery can run in process | Reject or separately review these at visual integration. Do not infer statelessness from HTTP or from empty implementation-task counts. |
| Existing replica field | HTTP 0.1–0.3 schema contains `replicas`; generator currently ignores it | It is not evidence of a running pool. P32 must distinguish the explicit versioned pool from this legacy hint and preserve old output. |
| Generated ownership | One logical API owns contracts, runtime archives, migrations and service source | Pool instances must execute that same source/artifact; they are not new C4 applications or independently generated APIs. Existing public/internal target identity should remain stable. |

P31 supplies only a separately packaged pool component and disposable consumer proof. P32 will define integration/refusal rules before changing generation. Existing QR recipes, starter archives and live applications remain untouched.

Using the released software version meets the repository's two-week release-age rule; the selected official image was rebuilt on 2026-10-21. The exact bytes are pinned, not a floating `latest`/LTS tag. HAProxy remains upstream GPL-2.0 software in its official image; the independent Jeeves definition/configuration code contains no copied proxy implementation.

The [HAProxy configuration manual](https://docs.haproxy.org/3.4/configuration.html) defines active health checks, DNS resolvers, round-robin balancing, connection/queue timeouts and soft-stop behavior. P31 disables retries and redispatch explicitly: replay of an ambiguous write is not inferred to be safe. A single local proxy and database remain failure points; the component does not provide public ingress, failover across hosts or capacity certification.
