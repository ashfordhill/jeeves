# QRWTY v2 field build and evaluation

Start with the shared backend that QRWTY and the independent v1 implementation (B) both built. Test whether the reviewed Jeeves design improves an observable outcome or makes the same change materially easier. A pass at the shared comparison leads to a complete v2 backend, a source count, two independent reviews and a local deployment rehearsal. A tie, loss or unresolved comparison returns a scoped verdict and the evidence collected so far. Public deployment and the later model experiment are separate decisions.

**Start a new agent with the [coordinator prompt](v2-coordinator-prompt.md).** The coordinator gives each fresh worker one [sequential assignment](v2-field-units.md). The independent evaluator owns the [black-box cases and decision rules](v2-black-box.md). The rest of this plan is the reference for inputs, release checks, backend line counts and the future experiment.

## Build sequence

Work through V01–V19 in order. They freeze the evidence, measure the untouched export, build the shared product flows and compare both candidates under the same failures and change request. V19 records **advance**, **stop** or **inconclusive** using the criteria fixed in V02. On advance, V20–V31 complete payments, customer journeys, measurement, release rehearsal and independent review. The coordinator records a local checkpoint and evidence for each assignment. [Assignments and acceptance checks](v2-field-units.md) · [Comparison rule](v2-black-box.md#decide-whether-to-continue)

Product-owned hooks, SQL and adapters can be written normally. If the generated boundary cannot express a required operation, record the smallest example and route the template repair to Jeeves. Keep work on independent flows moving. If a generator update is needed after G0, retain the first baseline and report the update as a separate interval with its cost. Archive any fresh export used for a second comparison. Never count completed QRWTY logic as part of an untouched baseline. [Source-count rules](../source-loc.md)

## Evidence required for a release candidate

Use the actual production-mode images, real PostgreSQL and cache, two copies of each HTTP process and two workers. Use the Pub/Sub emulator and controlled provider fixtures for repeatable failure cases. Also exercise the production adapters with designated Auth0 and Stripe test credentials where available. Carry forward matching generator evidence with its commit and identify which QRWTY application journeys were exercised. An emulator result establishes local behavior. A real provider or cloud observation gets its own evidence row.

| Risk | What the reviewer must be able to observe |
| --- | --- |
| Wrong user or service gets access | Sign in once and follow Browser → Account → Billing. Confirm separate caller and user checks, isolated reads/writes/exports, guest restrictions, CSRF, token expiry, concurrent refresh, logout and credential rotation. Inventory exposed routes on each image, including direct-origin access. Compare the generated database grants with the actual roles and queries. Check the dependency lockfile and release image against dated advisories and record the disposition of high-severity findings. Verify that logs and reports omit secrets, claim proofs and unnecessary personal data. |
| Someone follows a harmful or obsolete link | Use benign destination fixtures with allowed, blocked and unknown reputation results. Check exact QR destination, refusal and recovery when reputation is unavailable, operator-only blocking/reinstatement and propagation after edit, expiry, disable or delete. Test guest limits across replicas and a shared-address legitimate user. Verify a public report alone cannot take down someone else’s link. The browser harness intercepts destination navigation. |
| Clicks disappear or count twice | Independently match returned 302 event IDs to broker acknowledgements and persisted counts. A lost or uncertain acknowledgement returns 503 without a destination. HEAD records no click. Exercise broker/store outages, cache fallback, post-commit worker restart, replay, duplicates, quarantine, zero arrivals, cleanup boundaries and backlog recovery. Compare the database and broker records with the known input. |
| A customer is charged twice or gets the wrong plan | Test concurrent/retried checkout, signed duplicate or out-of-order notices, timeout after Stripe acts, stopped worker and recovery. Compare test-provider subscriptions and requests, inbox rows, entitlements and billed usage. No duplicate subscription or payment effect, no paid access from the browser return, and a billing-status read has no side effect. Verify cancellation, grace expiry, downgrade, account deletion, retained links and quotas. Show price/interval, pending status and cancellation consequences in the UI. |
| An ordinary mistake costs someone data or money | Drive create, claim, edit, disable, export, cancel and delete by mouse and keyboard on desktop and mobile. Check ownership, confirmations for irreversible actions, stale-tab conflicts, grace/delayed states, focus and accessible error recovery. Verify deletion and privacy promises after restoring a backup into an isolated environment. Keep human-only scan or accessibility checks visibly pending if they need a person. |
| The service becomes unsafe under load | Replay the same open-arrival mix on v2 and B with equal CPU/RAM, datasets, replica counts, warm-up and independent resets. Include hot links, cold/missing routes, mixed writes, cache loss, slow consumers and recovery. Record offered/completed/shed/failed requests, p50/p95/p99, resource saturation, DB connections, queue age and count reconciliation. The frozen launch profile uses 1M routes, 100 redirects/s for 60 minutes, a 1,000/s burst for 10 minutes, 10 creates/s and 20 account reads/s. Run it locally when capacity permits. Record any smaller envelope before the run and repeat each arm under the same conditions. Compare with the original targets of origin redirect p99 ≤200 ms, account/create p99 ≤1 s and healthy analytics freshness p95 ≤60 s. Report the demonstrated load and bottleneck, including harness saturation. [Workload and measurement points](https://github.com/ashfordhill/qrwty/blob/4f4940155eabb7b5e4dc4789f4c6137a61434725/docs/benchmarks/neutral-pack/v1.6/files/docs/plans/production-build/cloud-strategy.md#capacity-assumptions-not-tinyurl-measurements) |
| An operator cannot safely release or recover it | Give a fresh operator the export’s `deploy/contract.json` and `deploy/README.md` first. Record what they could configure from those files, omissions, wrong assumptions and any extra steps or time needed. Check ingress restrictions, TLS and secret bindings, primary/replica usage, per-copy pool budgets, cache loss, always-running workers, health, drain, migrations, rolling compatibility, restore and rollback. Rehearse with the same image digests and environment-only changes. Check alerts for payment backlog, click loss/delay and saturation. ## Independent assessment and handoff

Two fresh reviewers, preferably from different model families, receive the same code pins, behavior contract, tests and evidence. Give them neutral arm labels where practical. Keep prior verdicts and each other’s reports sealed until they have submitted independent ratings. Reuse v1’s 1–5 scale for service boundaries, layering, coupling, contract/error handling, concurrency/recovery, security, data design, tests, operability and maintainability. A 1 has material safety or design failures, a 3 has a sound core with meaningful weaknesses and a 5 has convincing verification. For each shared dimension give both scores, code references, observed results, confidence and which arm leads or ties. For mixed features such as analytics, compare common behavior separately from paid-tier rules. Examine refresh across copies, replay before unavailable dependencies, idempotent deletion, backlog survival and the default analytics date range where v1 had known issues. Reconcile disagreements against evidence. Keep service quality, feature coverage, benchmark numbers and spend visible individually. For major gains and regressions identify what came from the reviewed design, generated mechanisms, handwritten policy or deployment setup, and mark uncertain attribution. [Prior review prompt](../../../.docs/readme/v0/qrwty/evaluations/evaluation-prompt.md) · [Codex review](../../../.docs/readme/v0/qrwty/evaluations/codex-2026-11-16.md) · [Fable review](../../../.docs/readme/v0/qrwty/evaluations/fable-2026-11-16.md)

Publish an index under `docs/evidence/v2/`. Put inputs and hashes in `inputs/`, original and final neutral results in `oracle/v2/` and `oracle/b/`, workload data in `load/`, source reports in `loc/` and each independent review in `reviews/`. Link the feature matrix and usage ledger. In `release-decision.md`, answer three questions in plain language.

- **Did v2 improve over B on the shared backend?** Apply the V02 rule again to the complete shared evidence. Identify wins, ties, regressions and evidence gaps by feature. Report any new finding that reverses V19. Rate v2 billing against the frozen payment contract. Assess v2 user journeys against the public UX contract.
- **Could an operator deploy this candidate?** Give **ready for deployment rehearsal/promotion** or **hold**, with image digests, exact local evidence, open findings, owners and retest steps. A required 501, repeat payment effect, unconfirmed successful redirect, cross-account disclosure, unresolved critical/high security issue or failed restore is a hold. A blocked release-critical check keeps the verdict open until it has evidence.
- **What would have to be true before opening it to public traffic?** Identify the demonstrated workload, any unacceptable user harm and specific remaining live checks, such as managed IAM/TLS/origin restrictions, real broker/archive recovery, payment activation and target-region capacity. Give a verdict of ready at the demonstrated envelope, conditional on named live checks, or hold for repair. Assign an owner and the evidence required for each open item. A verified local release can still need these checks before taking customers.

## Optional future comparison using lower-cost models

Run this as a new controlled experiment after the main v2 comparison. A fresh prompt-only implementation supplies a contemporary non-Jeeves control. Historical B stays an additional reference for how the product was built the first time. Its different model, maturity and build history limit what the main comparison can tell us about the effect of handing a model a diagram.

| Arm | Starting material |
| --- | --- |
| Human-reviewed Jeeves design | Common product prompt and fixtures, the frozen human-reviewed v2 diagram, its untouched export and ordinary Jeeves use instructions. The model finishes the app. |
| Prompt only | The same product prompt and fixtures, an empty app repository and the common toolchain. The model designs and implements the app from scratch. |
| Model designs in Jeeves | The same product prompt, fixtures, Jeeves version and ordinary use instructions. The model starts with a blank project, designs its own diagram, exports it and finishes the app. Count diagramming time and failed exports. |
| Same reviewed design, implemented by hand | Give the worker the identical read-only diagram, settings and design explanations supplied to the first arm. It receives an empty app repository and ordinary coding tools. Withhold the export, generator and emitted source. Comparing this arm with the first measures the added value of code generation when design guidance is equal. |

Use these assignments if the owner starts the model experiment. Each gets a fresh worker. Keep its evidence and spend outside the field comparison.

| Order | Agent and output | Completion check |
| --- | --- | --- |
| 1 | Evaluator freezes the common brief, exact reviewed design, feature list, visible checks, held-out cases, input allowlist, budget and scoring before dispatch. | Remove the historical pack’s architecture drawings, execution briefs and solution hints from the common prompt. Record the diff from the reviewed diagram. A changed design carries its review or the label “derived from the reviewed version.” |

Give each builder only its row above and the common brief. | Pin model, reasoning setting, sampling settings, allowed help, compute, time and token caps for the matched group. Use the same evaluator-owned browser client. Assign any UI work equally and measure it separately. |
| 3 | One builder at a time submits timestamped candidate commits, visible-test repairs, the final commit and usage ledger, or the state at budget exhaustion. | The evaluator scores the saved submissions to measure time to first all-critical pass. Keep other arms’ code, results and hidden tests out of the builder’s inputs. |
| 4 | Independent evaluator reruns the frozen cases and the same sealed change on eligible matched candidates. Report outcomes per arm and group. | One matched group is four builds per model and is a pilot. Three independent groups are twelve builds per model if the agreed spend cap allows. Report actual counts, failures and spread. |

Pre-register primary outcomes as completion of shared behavior and release-critical failures within budget. Also report per-run generated share where applicable, performance, design scores, first-pass success, repairs, human minutes, tokens, cost and time to a passing candidate. Count budget exhaustion and incomplete runs. Publish all outcomes and their spread by model and arm, with blind independent scoring where feasible. Charge the provided design/export once in a first-use view and disclose its amortized reuse value. Keep this experiment separate from the v2 results and from the spend for a public deployment.
