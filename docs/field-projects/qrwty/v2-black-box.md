# How to test QRWTY and score Jeeves

The evaluator owns the inputs, expected outcomes and results. Run the same customer actions against any implementation that promises them. A monolith can use the same checkout test as a separate Billing service. The adapter supplies addresses, test identities, reset, clock, interruption and read-only observations. Business decisions belong to the implementation. Keep the frozen pack intact and give each new check its own version.

## Freeze the cases

In V02, make one row per promise. Give it an ID, applicable arms, whether a failure blocks release, starting state, operation IDs, ordered actions, exact interruption, evidence the interruption happened, independent observer, expected count or state, deadline and reset. Use the pack's timing bounds for its rows. Fix numeric deadlines for supplementary cases before running either arm. Commit the manifest hash, frozen pack version, scoring rules, configuration list, budgets and change-brief hash. V03 pins the new executable checker after calibrating it against the fixed rules and before evaluating either arm. Keep hidden fixtures, seeds, timing and change target with the evaluator until their scheduled release.

Unless an existing study budget specifies otherwise, give each change worker one 60-minute attempt on the same model and reasoning setting with no human coding help. Time starts when the worker receives its checkout and brief. It includes its local builds and tests. Record evaluator queue time outside that clock. Use equal token limits when the runner can enforce them, and report unavailable counters as unknown. Allow one diagnosed v2 product repair and one matched retest for the pilot. Checker or infrastructure repairs get their own attempt records on both arms. The stricter product deadline takes precedence over a test wait. Neither timebox sets a customer service target.

Use synthetic accounts and destinations. Use controlled Stripe, identity and reputation providers, real PostgreSQL and cache, and the declared broker or its named local emulator. Separate local, provider-test and cloud evidence. The pack only needs a public entry plus test controls for a customer case. If a case needs a particular queue boundary, label it as such. A missing equivalent observation is **blocked**. Preserve the public result separately when it is measurable. [Neutral runner and adapter contract](https://github.com/ashfordhill/qrwty/tree/4f4940155eabb7b5e4dc4789f4c6137a61434725/docs/benchmarks/neutral-pack/v1.6/oracle)

The required shared pilot set is the signed-in retry case below plus frozen rows **A05, A06, A10, A11, A16, A24 and F03**. Run the same set on B in V07 and on v2 in V16. The paid-purchase case starts after the decision. Define a material regression in the V02 manifest as a shared critical promise B keeps and v2 breaks, or a predeclared shared service target B meets and v2 misses under the same measured workload.

Use the pack CLI to list rows, validate each adapter and write a fresh result directory per attempt. Deliver one documented, non-interactive command for the supplementary cases. It must accept a saved case, adapter and output directory, return failure for an unmet expectation, and reproduce a selected case from a clean reset in local CI. Save the observed operation history, expected and actual outcome, run/commit/image hashes and artifact paths. Strip credentials from recordings. Recording a synthetic provider exchange is an optional shortcut when fixtures recur. An independently specified expectation decides whether a replay passes. A recorder UI is a separate project.

For a simulated charge claim, inspect the provider's full effects ledger for the expected test price, quantity and currency, including any later refund or cancellation. Count HTTP attempts separately. If the fixture exposes subscriptions alone, verify that claim and label the charge result unverified.

## Measure what the export supplies

Keep three observations separate. **G0** is the byte-verified stock export. **G0 with test hooks** uses a disposable copy of the same files plus the listed minimum product bindings. **Finished v2** has actual QRWTY policy. Hash the additions and verify the generated-owned payload files against the manifest after each run. Missing policy can legitimately prevent a bare G0 request from completing. Keep that row open for G0. Report each mechanism demonstrated with a probe in its own column.

| Generated promise to check in V05 | Smallest witness |
| --- | --- |
| One browser session survives concurrent refresh | Use two Browser copies, one signed-in fixture user and one protected identity echo. At expiry, both calls return the same user and the controlled issuer observes one refresh rotation. Record the shared session generation before and after. |
| A verified payment notice survives a lost reply | Hold the inbox commit and observe that success is withheld. Let it commit, interrupt the reply, restart and replay the same notice. Independently observe one durable inbox entry. Any credit for an applied benefit requires a separate observable effect at its declared product boundary. |
| A counted event survives redelivery once | Supply a small product hook that increments a value on every invocation, with no duplicate suppression of its own. Use the permitted product transaction. After commit, interrupt acknowledgement and confirm redelivery to another copy. Read the durable value independently. It must be exactly one. |

Declare these three promises from the reviewed design before measuring the export. Record a passed/failed/blocked result for each applicable configuration. An unconditional no-op, a duplicate-suppressing stub or an adapter that computes the answer can hide a broken composition. Count a promise as demonstrated only when all of its required configurations pass. Report **demonstrated promises / predeclared applicable promises** and **verified configurations / required configurations**, with the individual rows. Count repeated seeds as trials of the same promise.

List feasible pairs of replica count (one or two), broker binding (these two), and delivery condition (ordinary, duplicate or after recovery). Select cases covering every feasible pair. Always run the two-copy commit/lost-ack/redelivery sequence on **each** binding. Publish the selected configurations, pair coverage, exclusions and observed fault points. ## Measure a design change

In V02, seal one replay-policy change for the matched trial. Choose one shorter automatic replay window of 14, 21 or 28 days with the recorded seed. All are inside the accepted 31-day maximum. Keep receipts at 35 days and daily totals at 13 calendar months. Freeze boundary inputs, the shared regression subset, equal model/time/token and human-help caps, and a randomized arm order. List any old expectations explicitly superseded by the new requirement. Reveal the same brief to each change worker only after both starting commits are pinned.

Run on two separate disposable field copies, one from each pinned candidate. Supply only that arm's ordinary tools, including the pinned Jeeves generator for v2. Keep each patch outside both primary candidates. Pass when a first eligible event exactly at the new limit counts once, the first event just beyond goes to quarantine, duplicate delivery adds nothing, existing accepted receipts keep their original expiry, and unaffected shared checks stay green. Observe quarantine and totals directly. Record time to first passing change, agent usage, human minutes, repairs, changed product files, diagram edits and generated churn separately. If a neutral starting prerequisite is missing, report it and mark the maintenance comparison unavailable.

## Decide whether to continue

Count harm against original operations. Report duplicate active subscriptions per completed fixture purchase, missing confirmed events per eligible successful GET, wrongly counted events per known unique eligible event, and the actual versus expected totals. For each interrupted run report time from dependency recovery to the first verified correct state. Record sample sizes, affected IDs and seeds. An empty workload gives no rate. Keep first attempts, repaired attempts and missing evidence visible.

At V19 apply the following rule to the signed-in retry, redirect, click and maintenance cases fixed in V02. Include the shared access, ownership and moderation smoke checks specified in the assignments. At V31 apply it to all required shared release checks. An improvement over the earlier Jeeves build earns credit in the v1 A comparison only. A confirmed v2 critical failure or material regression takes priority. Otherwise require comparable evidence for the shared critical cases. A witnessed behavioral win can stand on its own if the maintenance trial is unavailable.

| Decision | Rule |
| --- | --- |
| Advance | All required shared critical checks for this stage pass on v2 with usable matched evidence, and no predeclared material shared regression occurred. At least one predeclared shared case passes on v2 and demonstrably fails on B, or v2 completes the correct change within the matched cap and B exhausts it. If both changes pass, an effort win counts only against a numeric material difference and repeat count frozen in V02. With no such threshold, record a tie. |
| Stop | Sufficient comparable evidence shows a tie, regression or no qualifying improvement. A verified v2 release-critical failure after the recorded repair allowance also stops advancement. Record the affected case and observed consequence. |
| Inconclusive | A required shared critical comparison lacks a working environment, equivalent observation, witnessed interruption or trustworthy checker. A behavioral tie with an unavailable maintenance comparison also lands here. Repair feasible harness problems and rerun both affected arms. If the gap remains, close the pilot with the missing evidence and next runnable check. |

For example, if both arms return the original link and count clicks correctly, and both pass the change within the cap, the default result is **stop, tie**, even at 65% generated code. If v2 returns the original link and B returns 503 on the witnessed replay, with all other required checks satisfied, the result is **advance**. If B's consumer interruption was never observed, the critical comparison is **inconclusive**. A duplicate subscription discovered after advance puts the release on **hold**.

On stop or inconclusive, publish the shared findings, G0 and partial backend count and actual spend. Label the candidate incomplete. After advance, the full comparison can still reverse the conclusion. Report any equally safe result achieved at lower cost as a separate finding. A single repeated payment effect blocks a v2 release regardless of shared design wins. Historical B's absent billing and UI go in the feature-coverage table. Provider-test and public-traffic claims each require their own evidence. [Release criteria](v2-build-plan.md#evidence-required-for-a-release-candidate)
