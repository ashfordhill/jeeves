## What the field run established

Finished arm A retained **3,548 generated backend lines out of 8,546 (41.52%)**. The other 4,998 were handwritten. All 11 stubs had been filled. The earlier 80.25% result covered guest creation alone. The measure excludes UI, product SQL, tests, infrastructure and A's edge Worker. The subsequent Web Analytics change was outside the measured backend. Arm B wrote 9,361 backend lines and omitted billing. Both independent reviews favored B on shared features, particularly its caller authentication, session refresh coordination and recovery of interrupted work. [A8 measurement and scope](https://github.com/ashfordhill/qrwty/blob/2ee2c1487838a94cf8824093d2c911d8df25737f/docs/evidence/a8/checks.md) · [Codex review](../../../.docs/readme/v0/qrwty/evaluations/codex-2026-11-16.md) · [Fable review](../../../.docs/readme/v0/qrwty/evaluations/fable-2026-11-16.md)

Three areas accounted for **3,800 of the 4,998 handwritten backend lines**. Sessions and accounts took 1,385, links took 1,286 and billing took 1,129. Browser session and forwarding can now take on shared work in the largest area. Link ownership and billing policy still belong to QRWTY. [A8 breakdown by area](https://github.com/ashfordhill/qrwty/blob/2ee2c1487838a94cf8824093d2c911d8df25737f/docs/evidence/a8/loc/areas.json)

The measured export used revision 84. The owner's project named “QRWTY · now (r84)” actually opens at **revision 85**. It adds an empty Microservice as a second destination of **Open link**. Both revisions have the same six blockers against the current generator. Five service calls lack workload identity, and the Session API call to Account API also lacks a compatible user-identity binding. These are regeneration findings against today's templates. ## What I would change

| Where the current diagram misleads | Choice in the saved proposal |
| --- | --- |
| Four services point at Identity with lines labelled “Calls.” The picture hides who actually signs a user in. A's two handwritten session/forwarding modules had a reproducible concurrent refresh race. | **Browser API** owns the one Browser session. Optional sign-in, guest context, offline refresh, 24-hour idle and seven-day absolute expiry are selected. Link, Account and Billing verify the user on the operations they serve. All five service-to-service calls authenticate the calling process separately. |
| “Create, manage & pay” points at both Session API and Billing API. Taking a Stripe callback exposed the billing tile through the generated edge and forced its user guard to Optional. In finished A the edge forwarded the callback through the browser facade, and a billing status read could drain work and call Stripe. | **Billing API is private**, with required user identity. A separate **Stripe event inbox** accepts machine callbacks. Both belong to one billing owner with separate database roles. The inbox role can select and insert provider events. Only Billing API can change subscriptions and export usage. A one-minute Scheduled task selects reconciliation work even with no browser traffic. |
| “Resolve and redirect” hides an entire correctness boundary in one Custom module. “Click events” still says Pub/Sub is pending in its description after the provider was selected. | **Redirect** has one Open link entry, an in-process **versioned Cache reader**, and a loader restricted to `published.link_routes`. A cached route is valid for at most 30 seconds from the primary lookup. An eligible GET must wait for the Pub/Sub publish acknowledgement, recheck validity, then send 302. Uncertain publish yields 503 without `Location`. HEAD publishes nothing. |
| Click aggregation and cleanup share one stub. A purged on delivery, so quiet periods also stopped retention. A simple counter would obscure deduplication, quarantine and the difference between delayed data and zero clicks. | **Click processor** consumes the Google Cloud topic. A Scheduled task handles retention while idle. QRWTY requires a receipt and its aggregate effect to commit together before delivery ACK. Account API sees named reporting views. It must check ownership, tier and pipeline freshness before presenting a count. |
| The saved ownership model lists four roles but no resource authorities, grants or dependency access. Guest admission relied on counters maintained separately by each Link API copy. Concurrent copies could admit up to the limit per copy. | Declare all store access. Redirect gets one routing view, Account API gets named owner/reporting views, and neither can write Links. Move **guest admission into Link-owned PostgreSQL** using an atomic per-key window. This removes a cache and puts one write per attempted guest operation on Links. A committed replay must be recovered before new-work checks. |

The original kept redirect independent of login and billing, and waited for durable click capture. Those are the boundaries worth keeping. The proposal has **16 backend tiles**, the same count as the measured design. The empty revision-85 tile is absent, and the dedicated payment ingress takes the place of the admission cache. In Jeeves both Browser API and Stripe event inbox must hang off an action lane. The system context identifies Stripe as the callback sender. ## Where generation ends

- **Stripe.** QRWTY accepts native events up to 256 KiB. The installed Webhook receiver speaks the Jeeves HMAC protocol and accepts at most 64 KiB. With the installed template, QRWTY's edge would have to check Stripe's signature, sign a smaller message for the inbox and wait for the inbox to save it before replying to Stripe. The proposed generator change lets the inbox accept Stripe's own signature directly. [Stripe implementation](implementation-notes.md#receive-stripe-notifications-directly) Generated completed work expires after seven days. Product SQL must retain a unique provider event ID and digest for 35 days after success, retain failures until repair and prevent a second payment effect on later redelivery. Stripe Checkout, portal and authoritative reconciliation still need provider code. The scheduled SQL callback can record due work. A Stripe lookup needs a separate integration. [Receiver protocol](../../plans/reliable-generation/evidence/rg17/protocol.md) · [QRWTY webhook contract](https://github.com/ashfordhill/qrwty/blob/2ee2c1487838a94cf8824093d2c911d8df25737f/docs/benchmarks/neutral-pack/v1.6/frozen/http-contract.md)
- **Clicks.** The Event counter retains seven days. The checked standalone receipt consumer tops out at 30 days, below QRWTY's **31-day replay and 35-day deduplication** contract. Aggregate clicks therefore stays a product stub with an explicit gap. The proposed generator change raises the limit and lets QRWTY choose how long to keep counted IDs and daily totals. The product still needs to handle bad messages and verify recovery from the archive. [Retention implementation](implementation-notes.md#choose-how-long-to-keep-clicks) A timer can run cleanup during idle periods, but its heartbeat alone cannot establish that all clicks arrived. [Receipt contract](../../plans/reliable-generation/evidence/rg18/protocol.md) · [Click requirements](https://github.com/ashfordhill/qrwty/blob/2ee2c1487838a94cf8824093d2c911d8df25737f/docs/plans/production-build/durable-clicks.md)
- **Sign-in and guest abuse.** The installed browser/workload contracts select Keycloak. Retaining QRWTY's deployed Auth0 login requires a supported integration and an end-to-end issuer check. The public services require the front-door stamp, which authenticates the edge's method and path. The product still needs a trusted, pseudonymous client-address key. The generated Rate limiter takes a verified user subject, so it cannot enforce the guest rule. The proposed database policy must be tested across copies. [Browser session contract](../../plans/reliable-generation/evidence/rg19/protocol.md) · [Rate limiter](../../studio-settings.md#distributed-admission-rg12) · [Front-door contract](../../../jeeves-generator/README.md#front-door-stamp)
- **Product behavior.** QRWTY still owns guest claim and secret replay, moderation, paid quotas, account erasure and recovery of uncertain provider effects. Each browser route must map its fields and responses explicitly. For example, a successful public CSV download spends one export allowance. Browser API must invoke an internal mutation with retry-safe quota accounting and render the returned rows as CSV. The generated internal GET handle permits reads only and its response format is JSON. The Web Risk tile needs a provider adapter. Product migrations and registered SQL must implement the declared views and grants. ## Evidence for this proposal

The reviewed Studio export is revision 4. Its 16 tiles and 18 modules have revised descriptions. When the v2 build was planned, live revision 6 matched this committed source apart from its revision number. The installed generator reported **nine template-backed module rows and nine stub rows**. The route loader counts as part of the Cache reader. Selected-source generation emitted seven application processes in 151 files, with zero generation findings and 24 required application or integration gaps. The generated deployment contract marks Browser API, Redirect and Stripe event inbox as stamped public services. Link, Account and Billing are internal. It identifies background work and the processes that support a database pool ceiling. Pool sizing, replicas and cloud resources remain deployment decisions.

I opened both projects, inspected the five new template instances by mouse, and exported Simple and Detailed views of the proposal. Every file downloaded from Studio matched the CLI export from the same saved source bytes. The exported extension checker and TypeScript build passed offline. Source diagnostics still list QRWTY's custom behaviors as unresolved. The export report records runtime verification as `none`.

This is an exportable scaffold. A QRWTY source-share measurement needs completed hooks and product SQL, the frozen behavior checks and a backend-only recount against this clean export. The 41.52% field result remains the comparison point. [Measurement method](../source-loc.md)
