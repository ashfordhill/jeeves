# @jeeves/analytics 0.1.0

Experimental bounded event-count component. The browser-safe main entry validates UTC calendar dates and builds 7/30/90-day presets. Dates are inclusive to users and translate to `[start, next-day)` UTC instants; valid years are 1900–9998, at most 90 inclusive days. Daily counts are zero-filled and unsafe integer counts are rejected.

The server-only `/postgres` entry creates an owned-resource event counter from reviewed generated descriptors: one owner-scoped parent with a text label, one internal child with an unambiguous belongs-to relation and timestamp field. It returns total events, total owned parents, active parents, daily counts and the top ten parents (count descending, UUID ascending for ties). Identifiers are validated; owner and dates are parameters. A read-only repeatable-read transaction gives summary/chart/top results one consistent snapshot and a five-second timeout per SQL statement. Connections release on success/failure. Never use request data to construct descriptors or accept a caller-supplied owner; bind the authenticated server principal.

This pattern follows the separation of authorization, range validation and relational aggregation studied in Umami (see `docs/reference/enterprise-architecture.md`). No upstream implementation code was copied. qrwty scans are the actual HTTP/Postgres consumer; a non-QR inventory descriptor exercises the same interface offline. Counts represent stored events, not unique people or completed downstream actions.

Range/result/time bounds do not certify capacity or provide admission control. Each query may inspect many events within the range; preserve the generated owner and parent/timestamp indexes, measure with production distributions and introduce a separately versioned aggregate storage design if needed. No caching, rollups, retention changes, geolocation or visitor tracking. Exhaustive load/chaos/security evaluation is deferred; the handoff records the focused evidence.
