# @jeeves/resource-workspace 0.1.0

Experimental account and owner-resource workspace for the current Jeeves REST 0.2 session/resource protocol. A validated finite definition supplies collection labels, actual fields and relations, selected operations, primary/table fields, page size (10/25/50) and Midnight/Paper visual preset. `createWorkspaceClient` owns same-origin fetch, session/CSRF state and protocol validation. `ResourceWorkspace` owns account access, cursor pages, record views, create/update drafts and relationship choices. Import the product-ui and resource-workspace styles once. `extraContent` is additive application content.

Each visible collection must have real owner-scoped list/read capabilities; create/update are optional. Internal records and parents without accessible owner list/read operations cannot be selected. Required relationship selectors page through that parent's API. Table/primary fields use actual scalar fields, identity or creation time; relationship choices remain in forms/details, avoiding a request per relationship in every table row. Schemas reject invalid bounds/identities/relations/display choices before mounting. Generation/visual binding is subsequent work, not supplied merely by importing this library.

The transport accepts only an API base on the current browser origin, without credentials/query/fragment. Cookies use same-origin requests; CSRF tokens remain in memory. No passwords/tokens go into browser storage or URLs. Mutations are never retried automatically. Timeout defaults to 10 seconds including the body (configurable 100–60000ms); JSON bodies are capped at 8 MiB. A lost response can leave an uncertain mutation outcome: check records before retrying. Empty 204 logout responses are drained. Session expiry or replacement clears identity, unmounts account data and makes old responses unusable. A failed session read is visibly distinct from an anonymous 401.

Input includes only declared writable fields/relations. Identity, owner and generated timestamps are never submitted. Optional empty values become null; updates resend required fields and relationships as mandated by the current API, and omit untouched optional fields (including existing empty strings). An unchanged form performs no write. A required text field follows the existing API's presence semantics and may contain an empty string. URL values must use HTTP/HTTPS without credentials; integer and enum bounds match the finite definition. The API remains the authorization and validation authority. Field labels do not define access rules.

Lists show the current bounded page with next/previous/refresh, not an invented total or whole-dataset search. This version has no delete, arbitrary filter/sort, optimistic concurrency token, password reset/email verification, SSO/RBAC, background refresh, offline queue, bulk edits or business commands. Editing a row submits changes against the API's current update semantics; it does not claim conflict-free simultaneous edits. The authenticated principal stays server-owned. The UI descriptor is a contract, never an authorization mechanism.

The released `@jeeves/product-ui@0.3.0` shell supplies consistent product hierarchy and responsive navigation. This implementation was informed by Payload's reviewed collection/authorization separation; no upstream code or dependency was copied. No live qrwty application or frozen recipe was modified. The P24 component proof uses a disposable Inventory API/database and the compiled archive. Later adoption must preserve the version/hash, generated ownership and these supported limits. Focused checks establish that envelope, not exhaustive production certification.
