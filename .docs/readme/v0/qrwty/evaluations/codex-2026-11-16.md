# Independent evaluation of QRWTY and Jeeves

**Reviewer:** Codex (GPT-6 family). **Report date requested:** 2026-11-16. Local inspection and offline checks were performed on 2026-11-15 UTC. This review was conducted alone, without reading the other evaluator's report.

## Executive summary

**60% is reachable for a QRWTY-like application, but it is neither achieved today nor a credible prediction from the remaining QL plan alone.** A's measured baseline is **3,548 retained generated lines and 4,998 handwritten lines: 41.52%**. My central estimate for QL06–QL14 is **895 existing handwritten lines replaced**, giving **51.99%** if equivalent source is emitted as templates. The largest remaining opportunity is Browser session. Its planned contract does not include all of QRWTY's guest handling, forwarding routes, account deletion or billing. Counting those as already covered would overstate the result. See the measured baseline and forecast method in §1; QL12's actual scope is [J/docs/plans/qrwty-lessons/units.md:884–959](/home/ash/github/jeeves/docs/plans/qrwty-lessons/units.md:884).

The four highest-ranked additions beyond QL are **safe BFF forwarding and guest context, durable inbox processing with fenced work, a Stripe provider feature pack, and atomic distributed admission**. Together with QL, they could replace about **1,700 lines**, producing an equivalent-source estimate of **61.41%**, with a broad **57.14–64.98%** range. This is an engineering estimate, not a new source-loc measurement. The actual generated implementation's size matters: at three-quarters of the replaced source size, the central result is **59.39%**. A fresh export and completed hooks must establish the eventual percentage. QRWTY's prices, quotas, ownership rules, moderation decisions and click semantics should remain application code.

**B has the better architecture and code in the shared backend scope.** Its advantages are operationally meaningful: workload caller authentication, explicit database grants and migrations, serialized session refresh, replay lookup before external dependencies, durable account-deletion progress, and a substantially more complete analytics failure/recovery path. A has sound pieces too: transactional link changes, sealed guest replay, ACK-before-302, receipt/effect atomicity, and particularly good fenced billing reconciliation. Its generated process wiring and ownership manifest are useful assets. I independently confirmed that all **71 template-owned/metadata files** match their manifest hashes. Neither shorter source nor a larger test suite is itself the basis of the verdict. Evidence and scores are in §2.

Three focused offline probes reproduced A's refresh race, owned-create replay ordering problem, and paid analytics default-range mismatch. A's existing **196 unit tests passed**; **227 selected B unit tests passed**. These results do not certify either arm's deployed behavior. B's historical reviews also disclose real weaknesses, including expired-cookie behavior and incomplete automatic backlog preservation when no worker runs. B has no billing or UI; their absence is excluded from the shared-area scores.

For Jeeves, prioritize **correct composition of existing primitives**, not merely additional boxes: finish the planned session/identity/scheduler work with stronger failure invariants; expose atomic cache and secure replay operations; give product SQL versioned migrations and precise grants; and make inbox/receipt processing reusable with retention and observable failure states. The experiment supports Jeeves as a useful generator, but not yet as a guarantee that a production-looking diagram implements all its production obligations.

## 1. Raising the template share

### Baseline and estimation method

The A8 measurement is **G0 3,572, R 3,548, C 4,998, D 24, total R+C 8,546**. Its source is `AD/evidence/a8/loc/source-loc-v2.json` at documentation revision `4f49401`; the root README's “Results after finishing A” table at that revision, lines 12–55, summarizes the same backend scope. B has **9,361 included backend lines in 77 files**; another **1,752 lines of configuration** are excluded by the metric's naming rule. I independently reproduced B's 9,361 using the installed parser and the same exclusion rules. A's measurement is the supplied, committed baseline; I checked its per-file C inventory and manifest hashes rather than re-exporting an application.

The manifest's actual field is `ownership`, with `generated-scaffold`, `generated-extension` and `generator-metadata` values—not literally a `status: generated` field. Template ownership and line provenance are related but different: the 4,998 C lines are the source-loc result, not “all lines of every extension file.” There are 53 retained template lines in the 48 files containing C. [A/.jeeves/manifest.json:1](/home/ash/github/qrwty/app/.jeeves/manifest.json:1); [J/jeeves-generator/src/source-loc.ts:24–75,83–92](/home/ash/github/jeeves/jeeves-generator/src/source-loc.ts:24).

For each candidate below, **S is my estimate of existing C removed, net of replacement hooks, adapters and declarations**. I inspected the cited functions, identified reusable mechanism, and discounted the whole-file count for policy and glue that must remain. Ranges reflect uncertain abstraction boundaries, not statistical confidence. They exclude SQL, tests, settings, UI and deployment. They also exclude new functionality that A currently lacks: adding a safety gate cannot honestly be called removal of existing A code. Candidate budgets are disjoint: keys are counted in P2, session authentication in P1, and neither is counted again in forwarding or encrypted replay.

The individual “share” column uses the explicit **equivalent-source assumption**:

`share(S) = (3,548 + S) / 8,546`.

This assumes a template emits approximately as many retained source lines as the handwritten mechanism it replaces. More generally, if the new template emits G lines and removes S handwritten lines, the share is `(3,548 + G) / (8,546 + G − S)`. Importing an external package does not automatically make that package's source generated backend LOC. No credit is given for padding generated source or moving product code into SQL. These distinctions follow the metric's parsed, nonblank-line and same-file retention rules, [J/jeeves-generator/src/source-loc.ts:24–75](/home/ash/github/jeeves/jeeves-generator/src/source-loc.ts:24).

### Failure and contract findings that drive the verdict

1. **A refresh can invalidate a valid session across replicas — reproduced with a deterministic offline fake.** Two callers enter `oidc.refresh` before either stores the new generation. The provider accepts the first token rotation, but its response is delayed; the second call gets `GrantRefused`, reads the old generation and revokes the session. The first response then cannot store because `revoked_at` is set. Both requests return `refused`. The scratch probe ran that interleaving against A's actual `accessToken`/seal/cookie functions; it did not emulate a real issuer or database. [AS/sessions.ts:110–143](/home/ash/github/qrwty/app/src/modules/session-api/session/sessions.ts:110); [A/infra/postgres/sessions/modules/session-api-sign-in-flow.sql:162–187](/home/ash/github/qrwty/app/infra/postgres/sessions/modules/session-api-sign-in-flow.sql:162). B locks the session before refresh ([B/src/session/store.ts:220–255](/home/ash/github/qrwty-baseline/app/src/session/store.ts:220)), with a real-database concurrency test ([B/test/integration/sessions.test.ts:200–224](/home/ash/github/qrwty-baseline/app/test/integration/sessions.test.ts:200), inspected, not rerun). B pays for that correctness with a database lock held across issuer I/O; a carefully fenced refresh lease is a worthwhile template design.

2. **A owned-create replay depends on reputation availability — reproduced offline.** A calls reputation and entitlement lookup before entering its idempotency helper. With a stored success available from the fake database and reputation returning unavailable, the actual handler returns 503 without consulting the replay. Guest creation correctly has an earlier replay lookup. [AL/create.ts:159–181,192–207](/home/ash/github/qrwty/app/src/modules/link-api/link-operations/create.ts:159); [AL/owned.ts:388–395](/home/ash/github/qrwty/app/src/modules/link-api/link-operations/owned.ts:388). B checks committed replay before reputation for both paths ([B/src/links/routes.ts:153–188](/home/ash/github/qrwty-baseline/app/src/links/routes.ts:153)). The generated helper correctly replays when called; **this ordering defect belongs to A's handwritten composition**, not a broken transaction implementation.

3. **A has the essential click commit ordering, but not the complete durable pipeline.** Its redirect awaits publish and rechecks expiry/state before 302; its SQL inserts the receipt and aggregate in one transaction before the generated loop ACKs. Those are real strengths ([AR/redirect.ts:249–263](/home/ash/github/qrwty/app/src/modules/redirect-service/redirect/redirect.ts:249); [A/infra/postgres/analytics/modules/analytics-worker-click-aggregator.sql:118–152,213–235](/home/ash/github/qrwty/app/infra/postgres/analytics/modules/analytics-worker-click-aggregator.sql:118); [A/src/runtime/module-clients.ts:598–609](/home/ash/github/qrwty/app/src/runtime/module-clients.ts:598)). A worker stopped after a low-lag commit can therefore leave `delayed: false`; redirect has no corresponding retention gate. [AA/routes.ts:232–249](/home/ash/github/qrwty/app/src/modules/account-api/link-analytics/routes.ts:232); [AR/redirect.ts:209–267](/home/ash/github/qrwty/app/src/modules/redirect-service/redirect/redirect.ts:209); acknowledged in [AD/evidence/a4/a-found-gaps.md:49–56](/home/ash/github/qrwty/docs/evidence/a4/a-found-gaps.md:49). ### What A owes to generation, and the overall verdict

Jeeves supplied A with **consistent per-tile processes, declared dependency slots, database login wiring, upfront stub-setting validation, caller verification, bounded admission/drain and reusable transaction/idempotency machinery**. The concrete output is visible in [A/src/processes/link-api.ts:54–153](/home/ash/github/qrwty/app/src/processes/link-api.ts:54) and [A/src/runtime/module-clients.ts:238–340](/home/ash/github/qrwty/app/src/runtime/module-clients.ts:238). The immutable-file check demonstrates that application completion did not require editing those generated files. This is valuable engineering structure and a credible regeneration boundary.

It did **not** force better domain layering than B: handwritten A code can import another service's private module, place a large workflow inside a route factory, or use a good transaction API in an unsafe order. Nor is a large set of Custom modules equivalent to implemented product behavior. In r84, sign-in flow, forwarding, link operations, moderation, redirect, analytics and billing are largely Custom stubs; the generated manifest identifies their `module-stub` selections ([A/.jeeves/manifest.json:1](/home/ash/github/qrwty/app/.jeeves/manifest.json:1)).

Several awkward choices are directly linked to the generated API: **AG-14** leaves workload identity to ingress workarounds; **AG-18** makes secret-bearing guest replay bypass ordinary idempotency; **AG-26** forces timeout races around clients that cannot observe the request deadline; **AG-31** leaves admission approximating an atomic operation with get/set. **Overall: choose B's shared-backend design as the stronger reference implementation, and A's generation/ownership model as the stronger development mechanism.** B's failure-path completeness and clearer reusable platform matter more than its larger source size. A proves that Jeeves can carry real applications, including billing, while preserving generated ownership. It also shows that a useful scaffold can constrain an application into weaker designs when its abstractions omit essential operations. Improve those abstractions before turning A's workarounds into templates.

## 3. What this says about Jeeves

Jeeves's strongest demonstrated property is that a diagram can generate **real, repeatable process and resource structure with an explicit customization boundary**. A preserved every template-owned file while completing substantial functionality. YouTube shows the next step beyond scaffolding: its cache and event-counter hooks describe product identity, eligibility and projection while the template owns the mechanism ([Y/app/src/modules/watch-api/watch-api-video-details-cache.hooks.ts:24–50](/home/ash/github/jeeves/field-projects/youtube/v4/app/src/modules/watch-api/watch-api-video-details-cache.hooks.ts:24); [Y/app/src/modules/view-counter/view-counter-receipt-and-increment.hooks.ts:8–31](/home/ash/github/jeeves/field-projects/youtube/v4/app/src/modules/view-counter/view-counter-receipt-and-increment.hooks.ts:8)). That is the right model for increasing generation share without making the diagram a programming language.

The weakness is uneven composability. A's generated runtime already contains good transactions, while secret-bearing replay still needs separate application machinery. Jeeves already has receipt/effect atomicity, but Custom consumers cannot straightforwardly get the appropriate receipt lifecycle. Cache readers exist, yet a redirect stub rewrites cache loading. Some policies are safer in handwritten B because its authors could use the database/cache/provider operations they needed. Evidence is in AG-18/26/28/30/31 and in [J/jeeves-generator/templates/local-v2/assets/src/runtime/receipts.ts.template:24–61](/home/ash/github/jeeves/jeeves-generator/templates/local-v2/assets/src/runtime/receipts.ts.template:24); [J/jeeves-generator/templates/local-v2/assets/src/runtime/event-counter.ts.template:30–66](/home/ash/github/jeeves/jeeves-generator/templates/local-v2/assets/src/runtime/event-counter.ts.template:30). A high generated percentage does not resolve these mismatches.

- **Read-only scope.** Used fixed-revision `git show`/tree searches, source inspection and scratch scripts. Wrote only scratch files under `/tmp/qrwty-eval-codex/` and this report. No other repository code/docs/manifest edits, branch, stash, commit or push. No other evaluator's report was opened. The historical B reviews were read because the brief explicitly includes them.

Reused individually linked installed dependencies; installed nothing. Tools/tests used the scratch working directories and disabled the Vitest cache. No application process, HTTP test server, database, Docker stack or cloud service was started; no studio port was touched.

Import analysis covers static relative imports/re-exports, not runtime dependency injection, HTTP calls or arbitrary dynamic imports. - **Historical evidence, not rerun here.** A's handoff reports 39 PostgreSQL integration tests and late billing checks ([AD/handoff.md:2193–2218](/home/ash/github/qrwty/docs/handoff.md:2193)).
