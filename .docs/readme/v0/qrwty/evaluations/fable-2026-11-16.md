## 1. Executive summary

**Template share**

- **Today: 41.52%** (measured, `A: README.md` "Results after finishing A").
- **With the planned QL06–QL14: about 51%** (estimate, range 50–53%), and 45% if the Browser
  session template is left out. The plan's own 49% and 64% came from B's line counts. A's code
  gives less: the Browser session template reaches 665 of A's lines, not 1,000; no QL unit
  touches billing (1,129 lines); and the scheduled task and workload tokens replace code A never
  wrote.
- **60% is reachable for QRWTY, but not with the plan alone.** It takes the whole QL plan (51%),
  six library changes (55%), and five canvas-level items (62%). A Stripe pack would add four more
  points (66%). For B's scope, without billing, the plan alone gives about 59% and the library
  changes about 63%.
- **The ceiling is about 65%.** By my classification 2,980 of A's 4,998 hand-written lines are
  product policy or provider-specific. So 60% needs nearly every generic piece generated, and
  every new product feature lowers the share again.
- **The measure misses SQL.** A wrote 1,342 lines of product SQL outside it. Counted as
  hand-written, today's share is 35.9%.

**Design verdict**

B is the better-engineered backend in every area both arms built: I score A 3 and B 4 on most
dimensions, with the largest gaps in operability (2 against 4) and tests (3 against 5). A reached
working features with far less hand-written code (3,869 lines without billing, against B's 9,361,
or 11,113 with its settings registry) and also built billing and a UI.

Jeeves's generated code gave A good structure at tile level: one process per tile, typed
dependencies only for what the diagram links, store ownership as database logins, and a
configuration pass. It gave A poor structure inside and between tiles: 25 source imports across
tile folders, ten lazy singletons, two idempotency implementations in one module, deadlines raced
by hand, and billing reconciliation inside a read route.

**Most valuable next steps for Jeeves** (beyond the QL plan; details in Task 3)

1. **Let the application's HTTP contract reach generated code:** one error renderer for the
   runtime, route tables, guards and templates; a `signal` on every client; message attributes.
   The planned Browser session's fixed 403 body can't meet QRWTY's contract without it.
2. **Make the module kinds the canvas already offers generate, in-process:** Rate limiter first,
   then External call. Both arms wrote 130–160 lines of distributed rate limiting; A's is inexact
   because the cache client has no atomic counter.
3. **Finish idempotency:** a replay check before side effects, sealed secrets, and a route-level
   wrapper. A's owned create doesn't replay first, and its guest create carries a second
   idempotency implementation.
4. **Give stubs a lifecycle and shared code a home:** `setup()` once per process, tile-level
   settings, and a sanctioned place for an application's shared contracts.
5. **Build a Webhook inbox after the Browser session, and check QL07 first:** a Scheduled task
   as specified fits one of A's four scheduled jobs.

**Separation of concerns and layering: A 3, B 4.**

- **B is better:** it has one consistent layer rule. Its domain functions still hold SQL.

**Coupling and "spaghetti": A 3, B 4.** See 3.1.

- **A:** 25 imports cross tile folders. `link-operations/contract.ts` is imported by 13 files in

**Contract consistency and error handling: A 3, B 4.**

- **A:** one `problem()` helper gives the product shape everywhere

  runtime's, the route table's and the guard's. Hence five wrappers (C5).

  - `QRWTY-Synthetic` is never honoured (`A: redirect-service/redirect/redirect.ts:240`).
- **B:** one error type, one renderer, 405 with `Allow` from `routeMethods`
  (`B: platform/http/server.ts:267-286`), replay before admission
  (`B: links/routes.ts:181-188`), and byte-identical replays (`links/routes.ts:101-110`).
- **B (recorded):** oracle rows A02, A03, A05, A06, A07, A10–A14, A24, R03, F01, F03, F06 and F09

**Correctness under concurrency and failure: A 3, B 4.**

- **A, sound:** the edit locks the row and compares the version in one transaction
  (`A: link-api/link-operations/owned.ts:186-193`). The claim and the guest create are single
  SQL calls. The redirect awaits the publish, answers 503 with the event ID on doubt, and
  rechecks expiry and validity (`A: redirect-service/redirect/redirect.ts:245-265`). The consumer
  records receipt and count in one statement before the loop acknowledges
  (`A: analytics-worker/clicks/aggregate.ts:82-96`). The webhook stores before 2xx and reconciles
  under a lease and a fence (`A: billing-api/billing/events.ts:84-100`; `reconcile.ts:48-95`).
- **A, weak:**
  - checkout calls Stripe, bounded at 8 seconds, inside a transaction holding a row lock
    (`A: billing-api/billing/customer.ts:241-285`; `stripe.ts:15`), under a 1-second Request
    timeout (`A: app/src/processes/billing-api.ts:29`), so the browser can get 503 while the work
    completes;
  - admission across copies can admit copies × limit (`A: …/admission.ts:14-16`);
  - a burst of misses over 16 reads fails at once, with no queue (`redirect.ts:194-197`);
  - retention runs only when messages arrive (`aggregate.ts:54-62`);
  - nothing stops redirects when the backlog can't be saved, which durable-clicks requires
    (AG-29).
- **B:** an in-process tier, a stale-fill guard and a queued semaphore
  (`B: redirect/route-cache.ts:33-140`); typed publish outcomes (`B: redirect/routes.ts:109-118`);
  commit then acknowledge in batches with a backlog frontier (`B: analytics/consumer.ts:1-6,
  57-80`); a safety gate (`redirect/routes.ts:78-81`); and it waits for dependencies
  (`B: processes/runtime.ts:179-197`).
- **B, open:** its own review left two medium findings unfixed
  (`B: docs/reviews/B07-review.md:319, 342`).
- **B is better.** A's database-level guarantees are good; its behaviour under load and outage is
  thinner.

**Security: A 3, B 4.**

- **A, sound:** PKCE, state, nonce and a binding cookie (`A: session-api/session/signin.ts:75-120`);
  no session fixation (`signin.ts:137-153`); `__Host-` cookies (`cookies.ts:11-31`); session IDs
  stored as hashes and tokens sealed to their session (`sessions.ts:43-50`); CSRF on every

- **B:** `openid-client`; workload tokens with per-route allowlists
  (`B: platform/auth/guard.ts:67-88`); an edge-signed client address

  column grants (`B: app/migrations/analytics/0002_pipeline.sql:86-102`).
- **B is better:** defence in depth. A's session layer itself is careful.

**Data design: A 3, B 4.**

- **A:** the database enforces its invariants: checks and triggers keep links tombstoned, bump

**Operability: A 2, B 4.**

### 3.4 Billing, on its own (A only)

About a 3. The design is right: signature before parsing, inbox before 2xx, state always read
from Stripe under a lease and a fence, Stripe idempotency keys, and a live key refused at startup

### 3.5 Verdict

**B has the better architecture and code.** It is stronger where enterprise software is usually
judged: failure behaviour, trust between services, least privilege, operations and tests. It paid
for that with 9,361 lines (11,113 with settings) against A's 3,869 for the shared scope, and with
heavy testing.

**A is stronger** in three ways: it needed far less hand-written code for each feature; its
platform is uniform and derived from the diagram; and it finished billing and a UI.

**What A owes to generated code**

- **Better structure, forced:** one process per tile from compiled configuration; a stub can
  touch only the stores its tile links, with read-only types for readers
  (`A: redirect-service/redirect/redirect.ts:47-50`); one writer per store as logins; route
  tables, transactions and idempotency records that A used well.
- **Awkward workarounds, forced:**
  - AG-14: no workload identity, so internal routes trust the network;
  - AG-18: a second idempotency implementation for the guest create;
  - AG-26: the redirect races the generated clients;
  - AG-31: a 129-line limiter that is still inexact;
  - AG-23 and AG-25: five error wrappers and duplicated contexts;
  - AG-33: reconciliation inside a read route.

**What A owes to its hand-written code:** the careful session layer, the database-enforced link
invariants and the billing design are A's own. So are the cross-tile imports, the uncached grant
calls, the unused deletion key and the missing sign-in tests.

## 4. Task 3: what this says about Jeeves

**Strengths the experiment shows**

- **The tile level comes free and comes right.** A wrote no platform or process code: 3,365
  generated lines stand where B wrote 2,806, plus 1,752 of settings
  (`A: README.md`, the "A now vs B" table).
- **The diagram constrains the code.** Dependencies, read-only access and store ownership follow
  the links.
- **The loop from field project to template works.** Gaps A found became four helpers, and A
  adopted all of them: `declareSettings` in 11 stubs, `defineRoutes` in 9 tables, `idempotent`
  in 3 routes, `transaction` in 2 (same README section).

**Weaknesses**

- **The share is scaffolding, not features.** Eleven of A's fourteen modules are stubs: ten
  Custom and one Data access (`A: docs/evidence/q05/jeeves/blueprint-v3-r84.json`). The
  catalog's Cache reader, Event counter, Rate limiter, ID generator and External call were all
  available and none fitted, mostly because a template is an HTTP route that a stub can't call
  (`A: docs/evidence/q01/checks.md:166-170`).
- **The platform is closed.** An application can't change a body limit, a timeout, an error body
  or a log line, so each mismatch becomes a workaround: 18 gaps from AG-18 to AG-35.
- **Operations are thin.** See operability above.
- **The measure flatters.** It ignores 1,342 lines of SQL and rewards generated bulk.

**The most valuable next steps, beyond the plan**

1. **An application-level HTTP contract (C5, C8).** Until the runtime, the route table, the guard
   and templates answer in the application's error shape, every new template adds a dialect.
   QL12 is the next one. It is cheap, and it unblocks conformance.
2. **In-process modules for kinds already offered (C1, C2, C9; QL09 is the pattern).** This is
   the difference between a canvas of tiles and a canvas of features. It also restores the scope
   rule: the Rate limiter and ID generator show settings that generate nothing
   (`J: docs/studio-settings.md:319-321`).
3. **Complete idempotency (C3, C4).** Both arms needed the replay check and the sealed secret.
   Without them A carries two implementations and a contract deviation.
4. **A lifecycle for stubs and a home for shared code (C6).** It removes ten singletons and gives
   A's 25 cross-tile imports a sanctioned alternative: one application-owned contracts folder,
   and a target per callee module in place of hard-coded `/modules/<id>` paths.
5. **A Webhook inbox (C11), after settling where scheduled work may run.** Billing holds 23% of
   A's hand-written lines and 45 generated ones. Decide the QL07 hosting question first: three of
   A's four jobs write a Service's database.

Alongside these, report hand-written TypeScript and SQL per feature next to the share.

**Where today's templates push applications towards poor design**

- **Module IDs are the API between tiles.** Callers hard-code `/modules/<module id>`
  (`A: session-api/session/forward.ts:54-59`; `billing-api/billing/grant-client.ts:9`), so
  renaming a module on the canvas breaks its callers at run time.
- **No place for shared application code.** One tile's folder becomes the library, and tiles
  import each other.
- **A stub is a function called per request.** State built once becomes module-level and lazy
  (C6).
- **`idempotent(fn)` wraps the whole answer in a transaction.** A stub that must call a provider
  to build its answer does so inside it (`A: billing-api/billing/customer.ts:241-285`). Offer a
  reserve-then-complete form, or say that outbound calls go first.
- **The admission answers at the Request timeout while the handler runs on**
  (`A: app/src/runtime/admission.ts:24-25, 58-72`), and clients keep longer fixed bounds. Stubs
  race by hand, and effects finish after the caller was told 503.
- **Product SQL is one re-run file per module, in a schema per module.** Hence five private
  migration ledgers, tables shared by convention (AG-35), blanket grants (AG-12) and views open
  to every login (AG-24). QG38 and QG39 address two of these; this review supports both.
- **Early gaps shape designs for good.** The missing transaction API pushed A's invariants into
  PL/pgSQL. QL03 removed the cause, and A1 then adopted `transaction` in two handlers only; the
  1,342 SQL lines stayed.
