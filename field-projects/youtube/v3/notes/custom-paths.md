# YouTube v3: custom paths in `app/`

`app/` started as a byte-for-byte copy of `generated/` in the commit `V3-12: v3 generated output`
([contract](../../../../docs/plans/youtube-v3/contract.md) §6). This table has one row for each
path that a later unit adds to or changes in `app/`. It says the area, the unit that made the
change, and what was written and why.

- **Areas:** hook, stub body, product SQL, UI or integration, plus test (product unit tests,
  outside `src/` and outside the LOC metric).
- **Not listed:** `generated/` (it is never edited), and the build and runtime output that
  `.gitignore` keeps out of Git (`node_modules`, `dist`, `dist-public` and `.runtime`).
- **Check (V3-17):** the rows must match `diff -rq generated app` with those four left out.
- **Scaffold edits:** none. No generated scaffold (`src/processes/`, `src/runtime/`,
  `src/features/`, `entry.ts`, `dependencies.ts`, `infra/`, `scripts/` assets) has been changed.

| `src/modules/video-contract.ts` | hook (new, shared) | V3-13, V3-14 | The product's video contract, shared by Upload API's multipart hooks, the Transcoder's hooks and the Lifecycle writer's hooks so the tiles can't drift. **V3-13**, from v2's `youtube-contract.ts`, `youtube-events.ts` and `video-paths.ts`: video metadata (title 1–200, description up to 5,000, channel), the start request (an `.mp4`, `video/mp4`, 1 byte–256 MiB, SHA-256), the completion answer, the original's key `upload-api-multipart-uploads/<videoId>/<uploadId>/source.mp4` (`ORIGINALS_PREFIX` is the multipart template's compiled prefix, because the lifecycle and Transcoder hooks get no prefix), the `VideoProcessingRequested` job bound to its original and to its stable event ID (v1's `youtube-v1` namespace, as v2 kept it), and `wireEvent`, which binds an event to its broker message ID. **V3-14**, from v2's `youtube-events.ts`, `youtube-contract.ts`, `video-paths.ts` and `public-video.ts`: each attempt's result prefix `videos/<videoId>/<jobId>/<attemptId>/` in Transcoded videos (the Transcoder's hooks get no prefix either); the `ProcessingStarted`, `ProcessingSucceeded` (with the template's HLS result, bound to that prefix) and `ProcessingFailed` (`INVALID_MEDIA` or `PROCESSING_FAILED`) events with their stable IDs; and the publication: `publicVideo` (the public record plus `visibility: "public"` and `state: "ready"`, its paths bound to the video), `VideoPublished` and its one ID per video. | `src/modules/upload-api/upload-api-multipart-uploads.hooks.ts` | hook | V3-13 | All of multipart's hooks. `principal` wraps the guard's `require` with v2's creator check: the realm role `creator`, else 403 `CREATOR_REQUIRED` (contract §2, question 5). `validate` is v2's policy: 413 `FILE_SIZE`, 422 `UNSUPPORTED_FILE`, 400 `INVALID_UPLOAD`, and the channel from the account's username. `metadata` and `response` are the contract's codecs. `originalKey` is the contract's key, and the factory refuses to start if the compiled prefix ever differs. `job` is the contract's job codec, for the outbox relay. `reserve`, `complete` and `closed` still delegate to the lifecycle, as generated. | `src/modules/transcoder/transcoder-segmenter-and-encoder.hooks.ts` | hook | V3-14 | All of the Transcoder's hooks, as v2's `youtubeMediaCodecs` and its `owns` checks: `job` is the contract's `requestedJob` (bound to its message ID); `video` gives the template its source (the original's key, size and SHA-256 from the job) and the attempt's own result prefix; `result` binds the HLS result to that prefix; `eventId` and `event` build the contract's processing events; `source.owns` accepts only an original under Upload API's prefix for the job's video, and `results.owns` only the job's own prefix.
