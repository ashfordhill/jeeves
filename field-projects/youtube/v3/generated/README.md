# Generated local v2 foundation

Experimental provider/project foundation. Inspect .jeeves/report.json for missing features and hooks. No application readiness or strict certification is claimed.

Node 24.21.0 and pnpm 12.16.1. Run `pnpm install --frozen-lockfile --ignore-scripts` then `pnpm build`. Set a unique `COMPOSE_PROJECT_NAME` and three distinct free loopback ports: `LOCAL_HTTP_PORT`, `LOCAL_IDENTITY_PORT`, `LOCAL_OBJECT_PORT`. Run `pnpm first-run` once, `pnpm stop` to stop all profiles and `pnpm start` for normal restart. Reuse those exact values and private .runtime with the original Docker volumes. No resets or credential rotation occur. An interrupted single-use storage bootstrap requires manual inspection.

Migration owners/admin are mounted only into setup. Runtime logins receive no implicit table access; features contribute explicit relation/view grants. PostgreSQL names are quoted and provider/composed-name limits refuse rather than truncate. Storage originals remain private; local public websites are a declared local-security limitation.

Cleanup only an owned disposable export: `docker compose --profile '*' down --volumes --remove-orphans` with its recorded project/ports, then remove its .runtime. Never run cleanup against a retained runtime.

Runnable processes: each application tile runs as `app-<id>` from `src/processes/<id>.ts`, healthy once its ready marker exists; HTTP processes answer `GET /healthz` on port 3000 inside the Compose network. `app-edge` publishes each public HTTP process at `http://127.0.0.1:$LOCAL_HTTP_PORT/api/<id>/` and answers `GET /healthz` itself; internal ones are reached only inside the network at `http://app-<id>:3000`. A module's routes are under `/modules/<module id>`: a stub or a generated hook in `src/modules/` answers 501 `NOT_IMPLEMENTED` until you write it. A consumer module or worker template runs a loop on its queue (a topic's `<topic>--<id>` subscriber): "Not implemented" sends the message to `<queue>.failed` with one log line, other errors retry within the loop's limit (a stub's 5 times, waiting 250 ms doubling up to 10 s), and `pnpm stop` drains the loops. Every store or channel a stub links to is provisioned for its tile with its links' widest access (a database login with CONNECT and USAGE on public, SELECT on the database's `published` views and on another owner's template views; a queue, topic or subscriber; a cache; a bucket key; a search service with no index), and `src/runtime/module-clients.ts` gives each stub real clients, each probed once at startup. Each module that writes a database has its own SQL file, `infra/postgres/<database>/modules/<module>.sql`, yours to write: `first-run` and `start` run it every time, after the template migrations and views, as the setup-only owner in schema `m_<module>`, so keep it re-runnable (`IF NOT EXISTS`, `CREATE OR REPLACE`). Only its tile's login uses that schema; every login on the database may SELECT what it publishes as views in `published`, and nothing else of its tables. `first-run` and `start` start them only while `processes.runnable` in .jeeves/report.json is true; its `processes.tiles` lists each process's routes, loops and provisioned stores. No restart policy: a failed process stays exited until `pnpm start`.
