# Local HTTP pool template 0.1.0

Attach to an explicitly upgraded HTTP service 0.4.0. Pair (default) or Trio selects two or three instances of the **same logical API**. An explicit local-execution 0.1.0 policy applies to every instance. Save changes the design; Generate changes files; neither deploys or restarts an application.

The supported shape is deliberately closed: REST API server 0.1.0 with session-backed owner resources, no domain extensions or implementation notes, one selected Postgres 0.1.0 store, no other behavior capabilities, a safe service ID/unprivileged port, and legacy replica hint one. Existing source is checked before any writes. Custom features, entry points, scripts/dependencies, database migration scaffolds, build configuration, unknown executable/configuration files and symlinks are refused. Normal documentation, known install/build output, display metadata and ordinary comments are allowed; Docker parser directives remain meaningful. Verification rechecks the recorded source fingerprints and ordinary generated-file hashes. This is a supported-shape contract, not analysis of arbitrary programs or a hostile-user security boundary.

After ordinary template fragments merge, the API's complete database/configuration/build/limits definition is cloned into `<id>-instance-1` etc. The original Compose name becomes the pinned P31 proxy, preserving internal clients and the logical loopback application port. Instance diagnostic ports also bind only to loopback. The generated proxy configuration, descriptor, guide and Compose are protected by ordinary ownership checks; lock metadata binds the instances and supported scaffold fingerprints. Credentials, data stores, contracts and public origins retain their original identities. Removal affects next-generation Compose; prior generated artifacts are reported as retained orphans.

Generation validates the frozen P31 manifest/archive and original definition source. It does not pull or execute a proxy image. The [P31 component](../../packages/http-pool/README.md) supplies the fixed limits, no-replay/readiness/DNS/shutdown contract and provenance. The proxy and database remain single failure points. No public ingress, global admission control, host failover, capacity, WebSocket/SSE or arbitrary-worker claim.

Baseline checks adapt their **test context** to this physical topology: HTTP lifecycle/configuration and local resource-limit checks run against each actual application instance; REST/browser operations use the logical proxy; Postgres checks read the application's resolved credentials. The pool pack sees the physical Compose and checks wiring/readiness. No Node check is run inside the HAProxy image. Existing unpooled behavior and previous template versions are unchanged.

`pnpm work run generated-http-pool` generates an editable starter, reviews its HTTP upgrade, selects Trio and local execution, preserves private setup/additive frontend content, runs the ordinary packs and strict resource browser journey, regenerates a visual preset and cleans the isolated consumer. `generated-http-pool-browser` selects only that browser journey and explicitly reports template packs as unselected; it is not full verification. The lower-level `local-http-pool` profile remains the frozen-component pair/failure-recovery proof. All run without implementation-model calls.

The pooled resource journey uses pinned Firefox 155.0 with unchanged strict diagnostics; editor and ordinary account-entry checks use Chromium. See the [browser diagnostic note](../../docs/developer-workflow.md#streamed-response-browser-diagnostics) for Chromium's reproducible no-store/manual-stream false-abort defect and small upgrade probe. This is an explicit engine limitation, not a suppressed failure or changed frozen client.
