# Resource workspace attachment 0.1.0

Experimental deterministic account/resource frontend for `web-app@0.2.0`, using the immutable resource-workspace 0.1.0 and product-ui 0.3.0 archives. Web 0.1.0 remains available with its original scaffold. The component's [supported protocol and limits](../../packages/resource-workspace/README.md) remain authoritative; no runtime was repacked for this attachment.

Connect the web app's REST client to a session-authenticated structured resource API. Add **Resource workspace**, choose that actual calls connection, select owner collections with list/read capabilities, then set labels, primary/table fields, page size and the Midnight/Paper preset. Required parent collections must also be available and selected. The frontend title comes from the web element. Field types, validation, operations and relationship names are derived from the backend contract; access is enforced by the server. The workspace transport has its own bounded ten-second timeout and never automatically retries mutations. Other REST-client transport settings do not override this component's protocol.

Configuration references stable resource/field IDs. Safe API names and display changes regenerate the descriptor; existing resource migration rules still govern storage. Invalid/incomplete bindings are visible readiness findings and cannot generate. Unsupported internal resources, missing owner parents, relationship cycles and invalid display references refuse before generated writes. The ordinary editor preserves incomplete diagrams so users can finish wiring them.

Generated-owned: `src/App.tsx`, `src/main.tsx`, `src/styles.css`, `src/workspace.generated.json`, ordinary API/proxy wiring, and both immutable component archives. Project-owned: additive `src/project/ProjectExtras.tsx` and supplemental tests. Notes produce narrow tasks limited to `src/project/`, `tests/` and the package manifest; component production dependency pins remain protected. Empty notes create no implementation task. The server reports this supplied capability explicitly, and refuses a changed protected workspace when reading a generated project for planning.

The lock retains attachment, calls connection, REST client, service and server identity. Removing or rebinding a published workspace requires reviewed ownership migration. Existing custom application roots are not implicitly adopted. Hiding a selected collection is a presentation change, not data deletion. No live application is regenerated by Save. Switching a generated preset requires generation/build and a page reload; it is not an unbounded runtime theme override.

`pnpm work run generated-workspace` generates a fresh non-QR Inventory application, proves no implementation tasks, builds actual archived components, runs the standard template packs plus account-entry pack, and reuses the P24 browser journey against the generated frontend. It regenerates and rebuilds the Paper preset while retaining records/session and custom extras. Strict browser diagnostics/axe and generated integrity stay active. The direct P24 `resource-workspace` profile remains available for the standalone compiled consumer. Ordinary stateful REST smoke checks retain their explicit skip reasons; the composed journey exercises the real account and record API.

C4 shows a generated workspace component and its actual calls edge, with additional notes as project work. This version does not provide arbitrary workflow/command screens, tenant administration, enterprise identity, conflict-free edits, cloud operations or exhaustive certification. Those require separate explicit capabilities and evidence.
