# Working with a web-app 0.2.0 element

Read the element's attachment list before editing. A `resource-workspace` attachment supplies the application root, entry, styles and resource screens. Its `src/App.tsx`, `src/main.tsx`, `src/styles.css`, `src/workspace.generated.json`, generated API/proxy wiring and frozen runtime archives are protected. Implement only additive content under `src/project/`, supplemental tests under `tests/` and explicitly permitted package additions. Keep the component dependency pins. The supplied workspace owns its same-origin cookie/CSRF transport; do not replace it with another login, form or fetch implementation. Use the workspace attachment guide for its supported behavior and boundaries.

Without that attachment, the ordinary scaffold is project-owned: build pages/components under `src/pages/` and `src/components/`, with layout/routing in `src/App.tsx`. Keep `startApp(...)` and the root element. API clients and runtime configuration are supplied by `@jeeves/web-runtime`; use `useApis()` and `useRuntimeConfig()` in custom components. nginx forwards the declared same-origin API paths. No secrets belong in browser code.

In both modes, preserve `src/jeeves.generated.ts`, `src/clients/*.generated.ts`, nginx configuration, Compose and vendor archives. Pin exact additional dependency versions. Expected error states belong in the UI; application console errors still fail verification. Standard web checks cover page loading, client routes, applied container configuration and applicable sample API calls; the workspace attachment adds its account-entry check. Independent component/application evidence is recorded separately.
